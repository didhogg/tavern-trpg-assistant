# 易错点（只写已核实的；没核实的明说）

## 一、作者写法约定（出处：作者自制仓库 README *Conventions to Follow*）

- tab 缩进、LF、UTF-8 无 BOM；文件名 `作者名; 自制名.json`。
- `json` 来源名全库唯一，不显示，可以长；没网址就填 `https://github.com/TheGiddyLimit/homebrew`。
- `authors` 只写内容作者，转换者写 `convertedBy`（格式相同）。
- 图片、角色卡 PDF 之类资源不放进 JSON 仓库，作者另有图片仓库；本项目的规矩也是只存链接，不存图片文件。

## 二、校验器怎么报错（出处：`src/library/brew-validate.ts`、`scripts/validate.mjs`）

- 作者的条目结构是“完整条目”或“`_copy` 加改动”二选一，校验器会把“缺 `_copy`”“不符合任何一种写法”一起报出来，那是陪衬。`validate.mjs` 有真正的错误时会去掉它们；报错太多只给最深的一条。**先改这一条，再重跑。**
- 错误位置（`/spell/3/level` 这样的路径）加行列都给了，直接去那一行改。
- 常见几种：`required`（缺必填键）、`additionalProperties`（多出结构里没有的键 → 多半是字段名写错或自己编的）、`enum`（只能取给定值之一）、`type`（类型不对，例如该是数组写成了字符串）。

## 三、本机作者样例的已知问题

- 作者自己的 `boon/Sample - Giddy; Dubious Gifts.json` 在本机这版结构定义（5etools-utils 0.17.24）下**不通过**：条目里多了 `ability`，结构里没有。**别照抄它的 `ability`。**
- 本机作者自制仓库副本是没有版本记录的快照（见 `tavern-trpg-data-next/report/说明.md`），和 0.17.24 结构是否配套没有核实，所以“样例里有、校验器说不认”的字段，以校验器为准。

## 四、和 TRPG 助手对接

- 插件里条目用作者编号（`name` + `source`）指，所以包里**条目名和来源名定了就别中途改**；同一个包里同名同来源的条目会互相覆盖。（出处：仓库 `AGENTS.md` 常驻规则）
- 交给结算内核时，没有英文对照的自制条目会直接把中文条目交进去，并标“无英文对照”（出处：`docs/handoff/D2-P3_性能改进二_验收修复.md` §2⑤，第 46 行）。
- 同一批文档记录过：中文条目直接转换在小样本里出过错（例：职业标识为空，准备法术公式变成 `@classes..levels`，出处：`docs/handoff/D2-P3-2_a_接手进度.md` 第 85 行）。**自制的职业、子职、种族这类会进规则计算的条目，在内核里实际表现好不好，本 skill 没有实测过。** 交付时要告诉用户：请在插件里把它实际加到一个人物上试一次。
- 中文自制：中文仓库在带 `name` 的对象上加了 `ENG_name`（英文名），本项目校验器已允许它（出处：`tools/build-brew-validator.mjs`）。
- **插件认一个自制文件是中文，看顶层条目有没有字符串 `ENG_name`**，并用它做显示、配对、英文名搜索（出处：`src/library/custom-lang.ts` 第 35–42、163 行）。所以中文自制的每个顶层条目都要带 `ENG_name`；没有它，这个文件会被当成英文自制。嵌套对象（特性、动作、引用）上的 `ENG_name`：校验器允许，项目里谁读它**没查过**；但**翻译英文包时要加**：作者中文样例里 12 个带 `name` 的对象 12 个都有（作者中文 fork 的本地化规则：译了 `name` 就把英文原名留在 `ENG_name`）。
- 中英自制包的配对按文件：同一目录 + `_meta.sources[].json` 有交集才配，条目先按**下标**取对面那条，**再核对名字**（中文条目的 `ENG_name` = 英文条目的 `name`），对不上就在配对的包里按名字找（出处：`src/library/brew-pairing.ts`；2026-11 全量实测 280 对里 18 对中文版重排过顺序，所以必须核对）。只做中文包时用不上；以后要给同一个包配英文版，条目顺序要一致。

## 五、真实试跑记录与由此得到的教训

试跑是 1 次（1 个只带这份 skill、没有背景的 AI，一次要它做 6 类 7 个条目：种族、专长、法术、怪物、子职加 2 个子职特性、物品，中文加 `ENG_name`）。样本只有这 1 次，下面只是这一次看到的：

- **结构校验第一次就通过**（我另外独立重跑过一遍，同样通过）。仓库里没有被它写入别的东西。
- **“过校验”不等于“没编内容”**。同一份通过的文件里，它写了用户没给的东西：种族已经有结构化的 `darkvision: 60`，又凭印象多写了一条“黑暗视觉”文字特性；还自己加了法术 `miscTags`、物品 `wondrous`、嵌套特性的英文名、怪物伤害平均值。已写进 SKILL.md 红线 3。校验器管不到这类问题，要靠交付时的“哪些是我填的 / 哪些是建议值”清单让用户核对。
- **法术、怪物没有 wiki 页**，它靠结构定义里的 `util.json`、`util-time.json` 和怪物样例才写对（学派编码、持续时间 + 专注的写法）。这些已补进 SKILL.md。
- **子职写法没有验证**：它写了 `className: "Fighter"`、`classSource: "PHB"`（照 wiki 例子），`shortName` 用了中文，只列了两个不同等级的 `subclassFeature`，没写 `refSubclassFeature`。都过了校验，但**在 TRPG 助手里实际加到人物上好不好用没试过**，也没核对是否合作者习惯。
- 校验器默认只显示“最可能的原因”那一条，一次看不到全部问题 → `validate.mjs` 加了 `--all`。
- **没做的**：把生成的包导入 TRPG 助手、在作者的 5etools 页面里看渲染；这个 skill 到目前为止只证明过“结构合格”。

## 六、做中文版（术语表翻译）的真实试跑记录

试跑是 1 次（另一个只带这份 skill 的 AI，把作者的怪物样例 `Sample - Giddy; Oaken Bolter.json` 译成中文版；作者自己有这份样例的中文版，事后拿来对照，**试跑 AI 没看过**）。样本只有这 1 份：

- 三项检查（结构一致、ENG_name、术语单）和中文版结构校验，**第一次都通过**；我独立重跑结果相同。
- 对照作者的中文版：结构、通用术语基本一致（名字、特性名、感官、传说组、`{@hit +6}`、`黑暗视觉 60 尺`、`受擒`）；原创名（动作名等）和自由句式各译各的，没有“标准答案”，这是预期内的差异。
- **暴露的真缺陷（已修）**：我原来的 skill 写“嵌套对象不要加 `ENG_name`”，试跑 AI 照做，12 个带 `name` 的对象里只有 4 个有；作者版 12 个都有。作者的结构比对脚本不拦这个（它允许、不强制 `ENG_name`），所以我给 `check-translation.mjs` 加了嵌套检查，并改了 SKILL.md。**检查全部通过 ≠ 翻得对**，这一条就是例子。
- 术语表命中（3 对真实中英文件，样本很小）：术语表里只有一个候选的词，4/4、1/1、44/52 出现在作者的中文版里；多候选 4/5；“没查到”的多是原创名。所以候选是证据，不能自动替换。
- 试跑 AI 自己补的旁证（`grep` 中文自制数用量）和自译，整体和作者版接近，但有一些措辞与作者版不同（如「受擒」之外的句式、`languages`、`immune.note`），无法判断谁“更对”。
- **没验证**：把中文版导入 TRPG 助手后能不能和英文版配对、显示（插件配对已核对名字，见第四节）；引用对象（`legendaryGroup`、`token`）的译名在站点里能否正确解析。

## 七、第三方作品译名步骤的试走记录

用作者自制库里真实的《巫师》职业包 `High Lord Amaram; Witcher Class.json` 试走这一步（只试步骤，没有产出译文）。样本 1 份：

- `brew-terms.mjs` 的“第三方作品判断材料”足以判断：来源是《巫师》同人职业，子职叫“某某学派”，法术名是 Aard、Axii、Igni，条目里有 Ursun、炸弹与药水。
- 联网查中文名的真实结果：搜到的全是攻略站和萌娘百科（粉丝 wiki），**没有官方简体中文资料**。按作者规则，搜索摘要和粉丝 wiki 都不能当证据。
- 读页面正文核实：3DM 攻略站（3dmgame.com）的页面里确实有“阿尔德之印、伊格尼之印、亚克席之印、亚登之印、昆恩之印”，但**页面没有英文对照，也没说是官方译名**；B 站两个页面取不到正文（空页面 / 验证码页），不算来源。所以只有 **1 个**核实过的二手来源，**不满足**“多个可靠二手来源”。学派名（狼 / 猫 / 熊 / 狮鹫）只在萌娘百科出现，更不够。
- 按作者规则的结论：这个案例**没有找到可确认的官方译名**，法印名只有 1 个二手来源。正确做法是保留英文或统一音译并报告不确定，不能写成“已核实”。这是这一步的**预期结果之一**，不是失败。
- **记忆会出错**：我自己的第一次查询把 Aard 写成了“亚登”，搜索结果纠正了（亚登是 Yrden、Aard 是阿尔德）。所以 SKILL.md 规定：没在页面正文里核实到的，不能填进 `evidence`。
- 旧的术语单（没有 `ip` 栏）过不了 `check-translation.mjs` 的第 ④ 项，要用新版 `brew-terms.mjs` 重新生成。

## 八、导入 TRPG 助手的实测（2026-11-14，Chrome，`tests/e2e/library/p58-skill-brew-import.mjs`）

输入：A = 作者怪物样例英文版 + skill「做中文版」译出的中文版；B = skill「生成」做出的试跑包（种族 / 专长 / 法术 / 怪物 / 子职 + 2 个子职特性 / 物品，只有中文）。样本各 1 份。

**通过的**
- A 中英成对：预览的作者结构校验两个文件都过；中文进中文那套、英文进英文那套；配成一对；3 个中文怪物都能用界面同一个入口（`otherEntry`）找到英文原件，英文名等于 `ENG_name`；`legendaryGroup` 引用能解析到同包的顶层传说组。
- B 只有中文的包：结构校验通过，6 类条目都导入并读回，`ENG_name` 齐全。
- C 进结算内核：战士建成并升到 3 级；用自制种族建人物成功，敏捷 +2 生效（10→12，和官方龙裔 +2 力量 +1 魅力同样生效）；自制物品、法术加成功；两个自制怪物建成；人物数据里没有 `@classes..`、`undefined`、`NaN` 之类的异常值。

**发现的**（都做了对照实验，不是猜的）
1. **带属性加值的专长，`entries` 里要有 `{"type":"list",…}` 条目（或至少一个 `type:"entries"` 的小节），只有纯字符串段落不行。**（精确条件读自作者渲染代码 `Renderer.feat.initFullEntries`：有可见 `ability` 时先找 list，没有就找 entries 小节，两者都没有才抛错。`validate.mjs` 已加这条警告，作者仓库 21 个真实专长包 0 条误报。）作者结构定义允许不写，但加到人物上时 Plutonium 报 `Could not find object of type "list" in "entries" for feat … when merging ability scores! Reformat the feat to include a "list"-type entry`。官方带属性选择的专长（如 Athlete）都有；试跑 AI 生成的没有。补上 `list` 后该报错消失（`variants-probe` 实测）。之后专长停在 `pending`（等用户在小窗里选属性）：官方的运动员、轻甲运用同一入口也是 `pending`，**正常，不是错误**。SKILL.md 已补这条。
2. **自制子职现在加不到人物上（插件现有限制，不是写法问题）。** 同一入口 `addToActor` 加官方 PHB 战士子职（战斗大师）成功；加试跑 AI 生成的子职失败，报 `Plutonium import failed`，控制台是 `Cannot read properties of null (reading 'classSource')`。我排除了写法：中文 / 英文 `shortName`、有 / 无 3 级介绍特性、全英文版，五种全部同样失败；**作者仓库里别人写的真实自制子职（Cosmic Domain，牧师）同样失败**。读 Plutonium 源码（`ImporterClass._pImportEntry`）：它收到子职时去自己的数据缓存 `raw_subclass` 取这个子职的原始数据，结算内核的数据源只有官方文件，取不到就是 `null`。种族、专长、物品、法术、怪物是直接把条目交给 Plutonium，所以能成。**自制职业很可能同理，没有测过。** 这是插件的问题，等驾驶员定怎么处理；skill 只能告诉用户“能导入、能读、能显示，但暂时加不到人物上”。
3. 每个子职导入后会出现**两行**：一行是原件（`className: Fighter, classSource: PHB`），一行是作者加载器另造的 `_isCopy` 副本（`classSource: XPHB`，给新版职业用）。核对导入结果时，别把“同名子职两行”当成重复导入。
4. 有英文版的自制包，交给内核的仍是**中文条目**（标“无英文对照”）：`kernelEntryOf` 用 `scoped.englishOf`，它只认官方的中英配对，自制配对在 `counterparts` / `brewPairs`。本次实测里这样交的种族、怪物、物品、法术都能成，所以没有出现问题；是否应该改成交英文版，等驾驶员定（和 NEXT 里“英文房规接进交给 AI 的条目：P12”同一类）。
5. 导入任何一个自制包后，读包列表 / 查询时控制台会出现 `local-set … 这个库版本是只读的` 的报错（小窗要求处理失败）。不导入时是 0 条；连合成的最小英文包也一样，**和 skill 生成的文件无关**，是插件现象，影响没查。

**测试环境的坑**：`profile-p3-1-chrome` 里的官方数据按“地址 + 端口”存；换一个没有数据的端口会报“English官方资料没装”。同一个探针只换端口，47342 成功、47345 失败。写新的 e2e 换端口前先验证。

**没有证明的**：这些自动测试只能说“通过 / 没通过”，不证明规则数值对；子职、职业进内核后的**规则数值**没法核对（子职根本加不进去）；没有 WebKit；没有界面验收。
