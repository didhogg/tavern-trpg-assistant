## 1. 验收发现的问题与根因

| # | 问题 | 根因（已证实） |
|---|---|---|
| 1 | 39 条 BMT/BGG 物品报“JSON 坏控制字符”（agent 判为作者数据问题，**错**） | 作者加载器**生成**的条目（魔法变体、怪物版本、亚种、专长版本，约 2,600 条）不在原始文件里，中文站作者的 `getEnglishEntity` 配不到 → 中文原件交给只认英文的 Plutonium；Plutonium 把法术引用编码成 ID 时按“一字符两位十六进制”（`Bundle.js` `UtilUuidFauxCompendium._getSerializedTagAndText`），中文解码成乱码。39 条只是报错冒头的 |
| 2 | 建人物 / 加到人物 / 读档重建**不读预换算缓存**，每次现场换算 | `runtime.buildCharacter` / `addToActor`、`rebuild.ts` 只交条目原文；只有批量建读缓存。`perf-user.mjs` 与诊断页“真机验证”都手动塞了换算结果，测试绕开正式路径 |
| 3 | 改任一自制 / 房规：全部换算钥匙失效，保存时原地重跑约 10 分钟，每次多 38 MB 旧数据 | 换算钥匙含自制包版本；但结算小窗只读英文官方文件（`host.ts` `libraryData`），看不到自制包 |
| 4 | 同一条目先后换算编号不同（职业成长步骤、效果改动等），缓存丢失 / 内核更新重换后读档卡“需要玩家选择” | T1 的“设种子就确定”不成立：换算开始时小窗状态不同——资料包懒加载时 dnd5e 给缺编号的子项补编号、导入器初始化、作者加锁（`VeLock` → `CryptUtil.uid`）都取随机数，把编号序列整体挪位（实测同一法术第一次 311 次、用过后 1 次） |
| 5 | 中文战役：自制条目加不进结算内核；房规生效时内核拿到英文原件，**房规被丢掉** | 违背蓝图“中文战役：没有英文对照的直接交中文条目，标‘无英文对照’”与设计 §2.3“有覆盖交房规版” |

## 2. 修法

```
① 生成条目配英文（library/english-generated.ts）
   生成条目 = 母条目 + 组内标识；母条目由作者写在条目上的出处字段给出（_versionBase_hash / _baseName / baseItem）
   版本 → 作者 getVersions 展开顺序；魔法变体 → 作者原始 magicvariant 的 ENG_name；亚种 → ENG_name = _subraceName
   结果：物品 3,513、种族 201、专长 9、传奇组 21 全配上；怪物 351/368（17 只中文数据写的英文名是母条目名，不猜）

② 编号只由条目本身决定（frame/importer.ts、frame/random.ts）
   规则 1：资料包加载进小窗时，补出的编号只由“哪个资料包、怎么取”决定（包一层 Foundry 官方 CompendiumCollection 取文档方法）
   规则 2：每条先预跑一次让它要用的缓存就绪，再按条目种子正式换
   不改作者 / 官方文件；固定测试 tests/e2e/library/kernel-determinism.mjs

③ 正式路径读缓存（cache.ts ROWS_OF 登记表）：建人物、读档重建、加到人物、批量建、重建怪物统一先查缓存

④ 换算钥匙 = 条目内容 + 官方数据版本 + 结算内核指纹（不含自制包版本）；人物重建基准钥匙仍含（房规会改生效版本）
   改自制 / 房规后补换算放后台（precompute-queue.ts），连续改合并；只换新的或改过的
   每行记“规则 + 内核指纹 + 官方版本”，完整换算后清掉同规则旧行
   有备选（房规、撞编号的包）的条目，备选版本也预先换好

⑤ 交给内核的条目统一一个判断（kernel/entry.ts）：原件 → 英文对照；房规 / 备选或无英文对照 → 中文条目 + 标“无英文对照”

⑥ 查英文对照提速：最近 4 类解析结果留内存（parsed-memo.ts，库一有写入全部作废）；结算内核查英文不读配图描述
```

诊断页“P3 全线后端真机验证”改走正式入口（建人物 / 批量建），真机点它测的就是玩家实际路径。
