## 1. P2 要做成什么（目标与边界）

P2 完成后，用户在【库】里能做到：

| 用户操作 | 应得到的结果 |
|---|---|
| 打开扩展包列表 | 按已接入的上游目录显示可用资料，不靠手写书单 |
| 选一本书或一个来源下载 | 插件调用作者的程序取数、解析、保存；显示成功或具体失败原因 |
| 打开包详情 | 看到这个来源实际包含的内容、类别、安装状态 |
| 浏览、搜索、筛选条目 | 查到已下载的数据，结果能打开对应详情 |
| 打开条目详情 | 正文、表格、关联引用按作者数据正确呈现 |
| 导入自己的 homebrew | 接受约定版本的 5etools 自制 JSON，走作者的自制内容路径 |
| 关掉再打开插件 | 已下载内容仍能读，不必重新下载、解析 |

分工边界（判断一段代码该不该写）：

```
 作者负责：解释数据（继承、引用、变体展开、正文渲染、搜索索引、自制内容迁移）
 插件负责：调用作者的程序、保存、管理（装了什么、什么版本、什么时候装的、启用没有）、查询、呈现
 红线：    作者数据必须先转成插件自创的内容格式才能用 → 就是走回旧路
```

"扩展包"可以继续当界面上的叫法，磁盘上不要求有 `.trpgpack` 文件。

"上游新增一个来源就能出现"的意思是：**在已接入、版本兼容的上游里，刷新目录后能看到新来源，不用改书单代码。** 不承诺"任意新格式都自动认识、任意新仓库都自动发现"。

## 4. 已暴露的问题

### 4.1 职业类 6 个类别取失败（E4）

```
 失败：class、subclass、classFeature、subclassFeature、classFluff、subclassFluff
 报错：ReferenceError: Hist is not defined（Chrome）；WebKit 同一位置 utils.js:4094
 原因（高度可疑，未重跑验证）：
   作者在 utils.js 第 4093 行用 Hist.util.getCleanHash 生成子职业编号；
   Hist 定义在 hist.js；E4 装的 16 个脚本里没有 hist.js；
   作者的 20 个核心脚本里有 hist.js。
 性质：试验的方法问题，不是作者程序或数据的问题
```

职业是人物模块最依赖的数据，B2 必须先把它跑通。

### 4.2 取数粒度粗（E3、E4、E2 §5 第 5 条）

作者加载器按"整类"取：要一本书的法术，会先取回全站法术再筛。一本 XPHB 共 347 个云端请求，8.8～24.8 秒。作者代码里对 GitHub 的失败有 15 分钟限流（`js/utils.js` 第 4848 行）。

### 4.3 E4 的通过标记是"未通过"

两个内核的 `passed` 都是 false，原因就是 4.1 的 6 个错误。除此以外，其余判定条件（宿主页没被改乱、存读指纹一致、云端请求全部 200）都满足。

```

 ✔ 不支持、取失败的内容明确列出来，不静默跳过
```
