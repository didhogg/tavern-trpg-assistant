# D2-P3 性能改进二：装资料时换算好 · 统一入口 · 种子修复（执行文档）

日期：2026-11-08。驾驶员已批准（2026-11-08 对话）。接在 `D2-P3_性能改进_交付.md`（S0→S6，提交到 `91acf83`）之后。做完停下等验收，**P4 不开始**。
权威顺序：`docs/handoff/D2-P3_整体设计.md` → `docs/handoff/D2-P3-2_结算内核实现蓝图.md` → 本文。冲突以设计为准并停下报告。

## 0. 为什么要做

上一轮验收没过，规划者实测出两类问题：

1. **种子要靠调用方自己设**：建人物前不手动 `setSeed`、导入时不传名字，存档就读不回（读档卡在“属性值提升”，证据 `work/e2e-lib/noseed-3b-chrome.json`）。上一轮把 `p3-3b-full`、`p3-4-full`、`backendProbe` 改成手动设种子，测试过了但问题被盖住。种子还用的是名字，重名 / 改名会出问题。
2. **第一次加入一条没用过的条目 0.3–2.8 秒**（怪物 1.7–2.2 秒，会施法的 NPC 2.8 秒，一次加 10 只新怪 3.4 秒；WebKit，`work/tmp/first-import-*.json`）。根因（`work/tmp/pack-callers.mjs` 实测调用栈）：
   - Plutonium 第一次要合并官方数据时，`CompendiumCacheBackendData._pCacheCompendium` 把 dnd5e 整个资料包 `getDocuments()`，每条建成完整文档（物品 885 条 0.6–1.1 秒、法术 320 条 0.4–0.55 秒）；
   - Plutonium 每类导入器第一次整理自己那一类数据（每类 0.25–0.45 秒，怪物约 1 秒）。
   - 换算一条本身只要 2–60 毫秒；读文件 5–9 毫秒。这些都是作者 / 官方程序的设计，每次开机重来，不改它们。

驾驶员已定（2026-11-08）：
- **下载装资料时，解析之后接着把 2014 能用的条目全部换算好，压缩存进【库】**；玩的时候只读不算。装资料多等几分钟换玩的时候全部即时。
- 2014 战役不用 2024：按设计 §1、§2.1 的规则范围，只换算 2014 战役看得到的条目。（结算内核换算时翻 dnd5e 2024 包只是“找对得上的官方条目”，Plutonium 按 `rulesVersion` 匹配，不是规则混用；不改它。）
- 用作者 / 官方的**统一入口**，不按类别各写一套换算或加入代码。

```
装资料（一次性，有进度）
  下载 ─→ 作者加载器解析（已有）─→ 结算内核用作者统一入口逐条换算 2014 条目 ─→ 压缩存【库】

玩的时候
  加怪物 / NPC / 载具 / 物件（单个或批量）─→ 读【库】─→ 一次批量建
  建人物 / 加队友 ─→ 内核生成人物种子并记进存档 ─→ 读【库】─→ dnd5e 官方成长流程
  加兼职 / 子职业 / 专长 / 装备 / 法术 ─→ 读【库】─→ dnd5e 官方“拖到人物上”流程
  读档 ─→ 用存档里的人物种子重建（S4 批量建照用）
调用方只交条目引用；设种子、换算、建卡全在内核里，不可能漏步骤。存档仍只存引用 / 选择 / 状态差别。
```

## 2. 步骤（固定顺序，每步一个本地提交）

### T1 统一换算入口 + 条目种子
- 结算内核里只留**一个**换算函数：`pGetImporter({prop})` → 作者导入器的导入方法 → 文档数据。作者导入器自己有专门方法的（例如职业）照作者的用；dataOpts 沿用现有登记表。
- 种子 = **条目自己的标识**（类别 + 来源 + 名字 + 内容摘要），在导入器初始化之后、导入之前设。同一条目在哪个小窗、排第几个换算，结果都一样。
- 删掉按类别分开的换算代码（`importEntry` / `importTemp` / `importMonsterData` 等改为调这一个函数）、“预热”补丁、`warmedImports`。
- 测试：每类自动抽样（不写死条目），同一条目在两个全新小窗里按不同顺序换算，结果逐项相同。

### T2 装资料时换算 2014 条目，存【库】
- 装官方资料、装 / 改自制包、改房规时，解析完接着跑“换算”这一段（同一个下载任务的一部分，进度照样报）。
- 换哪些：按 P3-1 规则范围，2014 战役看得到的（归 2014、2014 + 2024、全局通用的书和条目），且作者登记表有导入器的类别。**不写书单，不写类别清单。**自制 / 房规只换算变了的条目。
- 存储：浏览器自带的压缩（`CompressionStream`，不加依赖）后存进【库】；读时解压。实测并报告压缩前后体积。
- 钥匙改为：条目内容摘要 + 资料版本 + **结算内核指纹**（vendor 清单、结算小窗代码摘要、结算设置、规则）。插件更新而结算内核没变，缓存照用。
- 结算内核指纹变了：后端把换算标为“需要更新”，提供带进度的“更新换算”任务（界面 P5 再接）；没换完的条目照旧现场换算，结果写回。
- 能续：中途关掉，下次从没换的接着换，已换的跳过。
- 测试：每类自动抽样，存下的结果和现场换算 0 差别；改条目 / 改资料版本 / 改内核指纹都会作废，不误命中；中断后续做不重复。

### T3 建人物 / 读档同一条路，人物种子记进存档
- 新命令“建人物”：调用方只交条目引用和选择；内核生成人物种子（随机生成一次），按种子建卡，返回人物和种子。删掉 `setSeed` 命令和各命令的 `seed` 参数。
- 人物种子记进存档的人物记录；读档用它重建，不用名字。存档结构加版本并带迁移：旧存档没有种子的，按建卡时的旧规则用名字。
- 把上一轮加进 `p3-3b-full`、`p3-4-full`、`backendProbe`、`rebuild-cache`、`seed-order` 的手动设种子全部删掉，改调新命令。
- 测试：不设任何种子的全链路存档 → 读档 0 差别（规划者那份 `noseed` 测试作固定回归）；两个重名人物、改过名的人物、清空缓存后读档都 0 差别。

### T4 给已有人物加条目（官方拖放流程）
- 新命令“加到人物”：先试直接调 dnd5e 官方 `_onDropSingleItem`（无界面的人物表单实例）；需要界面就按同一顺序调同一批官方函数，代码注释写清对应行号。成长步骤沿用现有 `applyManager`（已记下选择 / 第一个可选项 / strict）。
- 覆盖：兼职（第二职业）、子职业、专长、装备、法术、消耗品叠加，全部走这一个命令。
- 存档：加进来的条目照现有引用 + 选择记下；读档按顺序重放。
- 测试：已有人物加第二职业并升 1 级 → 存档 → 清空缓存读档 0 差别；加专长、加消耗品叠加各一例。

### T5 怪物 / NPC / 载具 / 物件统一批量建
- 新命令“加人物（批量）”：交一组条目引用 → 读【库】换算结果（没有就用 T1 现场换算并写回）→ 一次 `createDocuments`。单个也走它。
- 录制工具补作者文件：把 Plutonium 原包 `data/` 里【库】不提供的文件全部带上（按目录比对【库】的英文官方文件清单算出来，**不逐个点名**），体积写进报告。
- 测试：怪物、会施法的 NPC、传奇怪物、载具、物件各抽样能建；一次加 10 只、50 只计时。

### T6 测速与全面验证
- `perf-user.mjs` 改用正式设置（`h.kernelInput`）；加每类条目“第一次加入”和批量的行；按 §3 全跑。
- `dist/` 进仓库，最后一次构建后提交。

## 4. 停下报告（其余不停）

1. 作者统一入口对某一类换不出来，且不改作者文件没办法。
2. T1 同一条目两次换算不一样，换两种方法仍不行。
3. 预换算与现场换算有解释不了的差别。
4. WebKit 上换算这一段超过 15 分钟，或压缩后超过 60 MB。
5. 需要改作者程序、dnd5e、Plutonium、Foundry 原文件，或新依赖。
6. 测试一步等超过 5 分钟（装资料最多 20 分钟）。

## 5. 不做

- 规则区分（已有，设计 §1、§2）；2024 换算（以后单独排）。
- 界面（P4/P5），包括“更新换算”的进度显示。
- 后台预热；结算内核体积裁剪。
