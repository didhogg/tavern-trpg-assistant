# D2-P3 性能改进：执行文档

日期：2026-11-08。驾驶员已批准草案（2026-11-08 对话）。P3 收尾支线，做完停下等验收，**P4 不开始**。
上接 HEAD（含 `b21436e` 结算模式关找图）。权威顺序：`docs/handoff/D2-P3_整体设计.md` → 本文。本文和设计冲突时以设计为准并停下报告。

## 0. 为什么要做

驾驶员要求：用户能感觉到的每一步（看资料、搜索、加条目、加怪物、结算、读档）都在 1 秒以内，**刷新酒馆以后也一样**。
办法定为：**能存的结果全部算好存进本地，平时只读不算**；用作者 / 官方现成的方法；**不做后台一直预热**（会占用酒馆本来就紧张的性能）。

驾驶员已定（2026-11-08）：
- **结算内核在进入战役时开机**（运行中的程序存不下来，只能选开机时机）；插件启动、看资料、搜索都不开它。
- **不做结算内核体积裁剪**：规划者实测能安全去掉的只有贴图解码、文件指纹、多边形计算约 0.47MB（开机脚本约 2%），开机时间看不出变化；其余去掉就开不了机或要改官方 / 作者文件（证据：`work/tmp/cover.mjs`、`work/tmp/trim-try.mjs`）。

```
                      改之前（实测）                 改之后（目标）
 刷新后点开“鸟羽人”    1.1–3.4 秒                     只读库（实测读库部分 0.05–0.13 秒）
 刷新后第一次搜“火球”  1.4–2.2 秒                     载入存好的索引（实测载入 73–77 毫秒）
 给英雄加战斧（用过的） 0.9–1.0 秒                     读换算结果，毫秒级
 遭遇里加鸟羽人（用过的）0.7–1.6 秒                    读换算结果，毫秒级
 读档（5 人）           3.7–6.6 秒（不含开机另计）     批量用存好的人物建，实测 50 人 0.8 秒
 结算本身               3–33 毫秒                      不变
```

## 2. 步骤（固定顺序，每步一个本地提交）

```
 S0 测速基线 → S1 装书时一次算好 → S2 编号按人物独立 → S3 条目换算结果缓存 → S4 人物换算结果缓存+批量建
 → S5 进入战役时开结算内核 → S6 全面验证
```

### S0 用户操作测速（正式测试）
- 新测试 `tests/e2e/library/perf-user.mjs`（Chrome / WebKit），按用户操作逐项计时：刷新后第一次看资料、再看一条、第一次搜索、加武器、加法术、加魔法物品、加怪物（第一只 / 之后）、攻击、伤害、施法、短休、长休、开战、下一回合、存档、读档（5 人 / 50 人，读档拆“结算内核开机”和“建人物”两段）。
- 起点可参考 `work/tmp/perf*.mjs`。**“刷新后”要真的重开页面**（同一 profile、**同一端口**），不能只在同一页面里第二次调用。
- 跑一次记基线进交付文档。

### S1 装书时一次算好，看资料 / 搜索只读库
- 在装书（`src/library/install.ts`）、开关书、改自制、改房规之后，用作者自己的加载器算好并存进【库】数据库：
  1. 每条的配图描述（作者 `fluffOf` / `pGetProxyFluff`，现有命令）；
  2. 每类每条“有没有被关”（作者屏蔽表，现有 `excludedFlags`）；
  3. 英文对象：**不再开英文小窗**，改读库里英文官方的解析结果（`storedItem('en-official', …)`）；
  4. 搜索索引：作者 `_pDoSearchLoad` 建好后用 `toJSON` 导出存库；刷新后载入。
- `service.detail` / `scoped.detail` / `query` 改为只读库；`search` 改为载入存好的索引后交作者搜索器出结果（作者的排序、设置照旧）。
- **第一件事先验证前提 3**：不改作者文件，能否把载入的索引连同那几样顺带算的东西接回作者搜索器。接不上 → 停下报告。
- 库数据库加新表 / 新键：`src/library/db.ts` 升版本 + 迁移测试。
- 存下的每份结果带“依赖钥匙”：对应源的提交号、自制包校验值、屏蔽表 / 范围设置、房规摘要。任何一样变了就作废重算。

### S2 编号按人物独立
- 每次建 / 重建一个人物（`commands-level.ts` `buildActor` / `rebuildCharacter`，`commands-monsters.ts` `rebuildMonster` / `importMonsterActor`）前，用这个人物自己的标识重新设种子（同一个随机源，不另写）。
- 证明：两个人物“先 A 后 B”与“先 B 后 A”各自编号逐项相同；先做别的导入再读档，编号仍与存档一致、重建 0 差别。
- 结构不变；旧测试数据重跑即可（没有真实用户存档）。

### S3 条目换算结果缓存
- Plutonium 换算结果（`importForBuild` 的结果、怪物导入结果）存进库。钥匙 = **实际喂给 Plutonium 的条目对象内容摘要** + 数据版本记号（`libraryDataVersion`）+ 插件版本 + `vendor/foundry/manifest.json` 版本 + `KERNEL_MODE_SETTINGS` + 规则。
- 建卡、加怪物、重建时先查缓存；命中直接用，没命中再换算并存回。
- **只实测、不实现**：装书时预换算核心书（PHB、DMG、MM）要多花多久、库要多占多少。数字写进交付文档，由驾驶员定做不做。

### S4 人物换算结果缓存 + 批量建
- 存档时把每个人物的重建基准（未叠状态的完整人物）存进缓存，钥匙 = S3 的钥匙 + 这个人物的引用与选择。
- 读档：全部命中 → 一次 `createDocuments` 批量建（保留编号）→ 叠状态差别；某人没命中 → 只给他重新换算（S2 保证编号一致）并存回。
- 存档本身不变：仍只存引用 / 选择 / 状态差别；缓存丢了一样能读档。

### S5 进入战役时开结算内核
- 当前聊天有战役、且这个战役已绑定结算内核时，在载入战役之后开机（`services.backend.kernel.session(ownerKey)`），不等它完成、不挡界面；开机失败要可见（提示 + `console.error`），不吞错误。
- 切换聊天（`switchOwner`）或读档换存档时：关掉旧战役的结算小窗（`kernel.close`），再按新战役开机。同一时刻只保留当前战役一个结算小窗。
- 没有战役、战役没绑定结算内核、只看资料或搜索时：**不开**。
- 读档流程（S4）用这个已经开好的小窗；没开好就等它开好，不重复开。
- 只做后端接线和启动时机，不做界面。

## 4. 停下报告（其余不停）

1. S1 第一步：作者搜索器不改作者文件就接不上存好的索引。
2. 任何缓存结果与现场计算有解释不了的差别，换两种方法仍不行。
3. 需要改作者程序、dnd5e、Plutonium、Foundry 原文件。
4. 需要新依赖或外部服务。
5. S3 预换算核心书的实测数字出来（只报告，不实现）。
6. 测试有一步等超过 5 分钟（装书最多 10 分钟）。

## 5. 不做

- 后台预热（除 S5 的“进入战役时开结算内核”外，什么都不提前开）；结算内核体积裁剪（驾驶员定不做）。
- 界面、图片缓存到本地（P4/P5）。
- 2014 战役用不用 dnd5e 2024 资料包的规则数据（驾驶员另定）。
- 结算内核断网时去 GitHub 查自制包索引（已登记在 `D2-P3_收尾_接线与真机验证.md` §5）。
