# P5 后端漏洞与重构

## 0. 建议执行的新后端架构（待驾驶员审批，尚未实施）

**建议：保留作者数据与程序，重构“安装计划 → 准备新版 → 检查 → 发布”这条管理路径。** 官方书、冒险、自制包的读取方式继续由作者决定；前端只选择对象、显示计划和结果，不再自己组织依赖安装、跨语言卸载、成功判定。

```text
玩家选择：安装这些书 / 更新这个包 / 卸载这些对象
                         │
                         ▼
现有 backend.library 统一接单（管理职责收回后端，不另起一套库）
  ① 计划：作者目录/加载器登记 + 真实包编号 → 文件、共享依赖、影响、预计新增字节
  ② 调度：同一资料环境的修改排队；所有入口共用任务、取消、超时、重试记录
  ③ 准备：作者原件原样下载；在隔离存储/派生结果里让作者程序解析
  ④ 检查：下载/镜像/解析/依赖/索引各自结果；可浏览与可结算分别报告
  ⑤ 发布：成功才一次切换可读版本，同时更新相关缓存的版本标记
                         │
       ┌─────────────────┴─────────────────┐
       ▼                                   ▼
旧版一直可读                        新版失败 / 取消
查询、书架、人物引用照常             保留旧版，显示真实失败与重试入口

只读接口：本机有哪些资料 → 浏览某书/包 → 本战役允许哪些 → 取生效条目
诊断接口：持久日志独立可读；体检按来源分别成功或报错
```

### 0.1 复用什么、变化在哪里

| 现有位置 | 建议变化（方式：修架构） | 保留的能力 |
|---|---|---|
| `plan.ts`、`directory.ts`、`download-estimate.ts` | 下载计划接收所选官方书/包；记录共享文件与依赖的使用者，估算和执行共用同一计划 | 作者书目、目录索引、现有文件清单；不手写书单 |
| `tasks.ts`、`service.ts`、`core/backend.ts` | 官方、自制、导入、更新、删除通过统一修改调度；按环境互斥，跨窗口/标签页也需版本检查 | 下载队列、作者 BrewUtil2 依赖安装、现有服务入口 |
| `files.ts`、`install.ts`、`brew.ts`、`db.ts` | 正在读取的版本与准备中的操作分开；原件、作者 KV、解析/备选/搜索结果准备好再发布 | 原文、作者对象与编号不变；已有数据迁移，不清库 |
| `brew-packs.ts`、`scoped.ts`、`removal-impact.ts` | 来源、安装包、条目版本分别定位；删除先算最终集合再算完整影响 | `docIdLocal`、稳定包标识、`EntryRef`、现有范围与覆盖关系 |
| `service.reset`、`ScopedLibrary.reset`、`EntryLinks.reset` | 发布成功统一通知版本变化，按依赖失效；读取一次绑定同一个可读版本 | 已有配对、排序、定位、结算缓存，不全部重写 |

以上是职责与行为建议，**不是新条目 schema，也不是已存在的新 API**。若需新增操作记录、可读版本指针或文件版本键，只能是插件管理信息；必须在实现方案里说明数据库迁移、旧缓存识别与异常恢复，单独审批后落地。

### 0.2 必须守住的行为

1. 一本书可能使用多个作者文件，一个作者文件也可能包含多本书。按书安装是用户选择单位，不保证网络上一个文件只含这一本；共享文件不改写、不重打包。
2. 共用文件已下载不等于其中所有书均已安装。未选书不能被共享文件、全站搜索索引误报为已装；被直接引用的依赖要说明来源与用途。
3. 官方按来源拆文件的类别优先调用作者单来源入口；共用文件和跨条目依赖沿作者声明/加载过程确认。P4 的“缩小读取索引”仅是探测结果，正式采用需验证；云端原始索引不覆盖修改。
4. 作者程序启动需要的基础文件作为明确依赖保留；卸载某书只回收没有其他使用者的文件。我的库仍可管理/导出；需要依赖才能展开的副本要保留依赖或明确报告，不能声称副本完全自足。
5. 准备新版时读取旧版；成功后发布新版。数据版本必须反映已安装来源集合、作者原件/自制包版本及相关程序版本，不能只靠全局提交号。
6. 自制写入要在隔离的作者存储中准备，不能只保护解析结果却提前修改正式 KV。发布包含原件/作者存储、解析、备选索引和状态；失败不得“报原内容没改动”而实际已改。
7. 官方多书共用仓库版本。若新书需要新仓库版本，必须列出对既有书和共享文件的影响，或使用当前版本；不能悄悄形成无法追溯的混合版本。
8. 删除检查读不到就是检查失败；执行必须对应同一份完整计划并重新核验版本。用户数据库与库数据库分开，不宣称一个 IndexedDB 事务可以跨两个数据库。
9. 浏览本机资料不等于战役启用；开关只控制战役使用。修改资料不得修改当前战役选择和选书设置。
10. 先审批后端变化并验证，再审批受影响的前端接线；做前端时若又发现要改后端，必须停下报告，禁止顺手改。

## 3. 逐项修法与调用点

### H1｜官方按书安装未接通

- **核实依据/漏洞处**：`src/library/tasks.ts::startOfficial(setId)` 没有书参数；`install.ts::installOfficial` → `plan.ts::precachePlan` 取整套预载。`ui/libview/DownloadTab.vue::startOfficial` 和模板展示“一键安装全部”“不能单本下载”。
- **不能混淆**：`startAdventure(setId, adventureId)` 和 `service.brewAddUrl/brewInstallSources` 确实已存在；作者 `DataUtil` 的多来源读取实现有 `pLoadSingleSource(source)`。P4-0c 记录部分下载探测成功，但没有完成英文配对、依赖、审计和真机验证。
- **方式：修架构**。在现有计划层形成“选中书/包 → 原始文件与依赖 → 安装记录”的统一计划；共享文件原样保留，作者程序解析，发布时只将所选书及明确依赖标为可用。安装/更新/大小估算使用同一计划；全装保留为可选批量操作。
- **调用点**：后端 `directory.ts`、`plan.ts`、`download-estimate.ts`、`install.ts`、`tasks.ts`、`core/start-campaign.ts`；审批后的前端调用方为 DownloadTab、读档缺包下载、冒险阅读器和下载重试入口。
- **验收**：选少量书而非全选；记录实际请求文件、网络字节、复用文件、依赖、安装来源集合；未选书不冒充已装；断网重开可读；中英与结算取条目均验证。

### H2｜更新提前切换版本，无完整失败回退

- **核实依据/漏洞处**：`official-update.ts::apply` 先 `files.modify` 改未变文件提交号，再 `setCommitOverride`，最后 `startOfficial`。`db.ts` 的原件主键为 `[source+path]`；`files.ts::get` 覆盖同一路径，`local` 又要求提交号相等。
- **方式：修架构**。活动版本保持不变；下载/解析使用明确的目标提交和准备区，不能改全局指针；检查成功再发布。准备区需覆盖作者 KV 和派生结果，不能只临时保存文件；启动时识别中断操作而不是把未完成目标当成当前版本。
- **调用点**：`OfficialUpdates.check/apply` → `DownloadTasks.startOfficial` → `installOfficial` → `FileProvider`；`hydrateCommits`、数据版本提供者及读取小窗也要读同一活动版本。
- **验收**：在更新每个阶段断网、解析失败、关闭页面、重开；旧版文件、条目、来源开关仍可用，失败目标能重试。未变化文件复用，不宣称更新必定传输全部约 150MB。

### H3｜任务状态覆盖可读状态

- **核实依据/漏洞处**：`install.ts` 一开始 `setRecord('downloading')`，随后 `parsing`；`scoped.ts::installed` 与 `service.ts::officialInstalled` 只认 `installed`；`scoped-search.ts` 对官方未安装直接返回空，自制也被官方状态连带排除。
- **方式：修架构**。独立表达“当前可读版本”和“操作进度”；查询只根据已发布版本，进度只影响操作按钮。首次安装确实没有旧数据时才显示未安装。
- **调用点**：上述函数、`BrewPacks.list`、`BookDirectory.load`、`starter.dataStatus`、`stores/libview.ts::load`；不能只把界面的空态遮住。
- **验收**：已安装库更新期间，书架、搜索、按编号取条目与自制资料继续读取旧版；首次安装和失败重试的状态仍准确。

### H4｜自制重解析先清旧结果

- **核实依据/漏洞处**：`brew.ts::parseBrew` 在 `openFrame()` 前删除 `parsed:<自制集>:` 并失效缓存；包的装删更新先在正式作者存储完成，再调用重解析。报告和其他索引可能停留在旧状态。
- **方式：修架构**。在隔离的作者 KV/同步存储和结果区完成修改、解析、备选索引与检查；成功发布，失败保留旧可读版本。作者内容问题可以呈现部分可用，但必须逐项标明，不能悄悄丢掉旧的健康内容。
- **调用点**：`service.ts::brewAddUrl/brewInstallSources/brewImport/brewDelete/brewPull/afterBrewChange` → `parseBrew` → `buildAlternatives`；复用 `openFrameIn`、现有预览隔离机制，注意同时处理同步和异步存储。
- **验收**：新窗口启动失败、任一类别解析失败、存储满和依赖失败；原始包与上一版可读结果均可追溯；不先清整套自制库。

### H5｜失败安装被任务标为完成

- **核实依据/漏洞处**：`install.ts` 根据镜像、解析/正文失败记录 `failed` 并返回报告；`tasks.ts::startOfficial` 只因 `download.failed` 抛错，外层 `start` 把正常返回记为 `done`。换算错误也仅写 `convertError`。
- **方式：漏洞修复**。让安装结果明确返回是否可发布；任务消费完整结果。把资料可浏览、结算准备失败等分开，不把所有 warning 一律变致命错误，也不把错误吞成成功；与 H2 的发布门统一，避免再造第二套判定。
- **调用点**：`installOfficial` → `DownloadTasks.startOfficial/start` → `stores/downloads.ts::refresh` 的“资料已就绪”；自制调用者同时消费 `parse`（见 M8）。
- **验收**：下载成功但初始化/类别/正文/镜像失败均不报整体就绪；换算失败准确标出结算未准备好，能够单独重试。

### H6｜删除检查读失败放行、连带影响漏算

- **核实依据/漏洞处**：`core/removal-impact.ts::impactOfRemoval` 用 `.catch(() => [])` 吞包清单失败；`removedOf(target,packs)` 在传递依赖计算前生成，后面房规、版本选择、存档检查仍用最初对象，没有包含 `removeTogether` 的全部包。
- **方式：漏洞修复**。清单读取失败返回检查失败并禁止执行；先求最终删除集合，再用完整集合重建 `Removed` 并扫描影响。若同一来源仍有其他包提供，须按作者选择与真实依赖关系判断是否真的失去依赖，不得只凭缩写强删。
- **调用点**：`impactOfRemoval/removedOf/refGone/whyKernel` → `ui/libview/actions.ts::removeSource`、`MyLibTab.vue::remove` → `service.brewDelete`；最终执行入口也要校验计划/目标仍有效，不能只信前端传来的编号。
- **验收**：删 A 连带 B、C，只引用 C 的存档/房规/选版本必须列出；读包失败不执行；检查后新增包/依赖时拒绝过期计划或重新确认。

### H7｜多套卸载范围不一致且可只删一半

- **核实依据/漏洞处**：`ui/libview/actions.ts::removeSource` 只预览 `row.set`，执行循环 `[row.set, en-official]`。`uninstallOfficial` 每套单独事务并各自查正在运行任务；第二套拒绝时第一套可能已删除。英文行只得到一个英文目标，并非总是中英一起。
- **方式：修架构**。前端提交明确对象集合，后端先对全体检查并生成同一计划，再作为同一库操作执行。官方本地文件/派生物/安装状态在库数据库内统一发布删除；作者 KV 的变更/窗口通知应与成功结果一致。涉及用户存档只读影响，不跨库强行宣称事务原子。
- **调用点**：`removeSource`、`backend.removalImpact`、`backend.library.uninstallOfficial`、`uninstall.ts`、`core/backend.ts` 的 afterDelete；按书卸载继承 H1 的共享依赖回收规则。
- **验收**：第二语言正在下载时任何目标均不先删；预览与执行范围完全相同；中途异常不谎报“原有内容没有改动”。

### H8｜来源、安装包和条目版本身份混用

- **核实依据/漏洞处**：① `scoped.ts::catalog/sourceCounts` 从解析结果的 `source` 造自制行，不保证有对应包；② `actions.ts::brewPackOf` 按来源 `.find` 第一个包；③ `ShelfTab.vue::mineSources/match` 把所有同来源行排除，包括官方原件；④ `pack-data.ts::loadPackRows` 仅用 `setId` 取类别，实际 `scoped.query` 跨本套所有数据集，未按指定集/包限定结果；⑤ `EntryLinks.corpusIndex` 将自制书目直接 set 到官方同一个 hash 键，遇同编号副本会替换原件定位，不是保留两个提供者。
- **方式：修架构**。目录行带真实安装对象与提供者：官方按书/来源，自制按作者包编号及稳定标识；来源是内容出处，不能替代包编号。浏览或删除用选中对象直接定位；复制件与原件同来源仍独立存在，备选关系沿用已有实现。
- **调用点**：`BrewPacks.list`、`ScopedLibrary.catalog`/浏览查询、`CatalogRow`、`packStableId/EntryRef`、`loadPackRows`、`ShelfTab`、`actions`、`MyLibTab`；已有 `brewDocIndex`、`variant.docIdLocal` 应复用。
- **验收**：同来源两个包、同编号备选、官方存副本后两者并存、一个包多个来源、包内不混入其他包。不采用“凡官方缩写就隐藏自制行”的遮掩办法。

### H9｜修改流程并发竞争，局部失败重置全部共享窗口

- **核实依据/漏洞处**：`DownloadTasks.start` 只去重相同 kind/set/item；自制修改直接走 service，`BrewCatalog` 仅阻止同一行重入；`afterBrewChange/withTimeout` 调 `service.reset()` 关闭所有 codeSet 的共享小窗。卸载只查 tasks，没有自制操作登记。
- **方式：修架构**。同一作者数据环境修改串行，读者绑定已发布版本；每个操作使用专属准备窗口/取消信号，超时只清它自己的资源。作者包管理器内部锁只管作者函数，不覆盖插件的重新解析/发布全流程；跨标签页也需锁或版本比较。
- **调用点**：`tasks.ts`、service 全部修改入口/`reset`、`uninstallOfficial`、`BrewCatalog.download`、`core/backend.ts` 接线与后台换算队列。
- **验收**：两包并发安装、安装同时删除、更新同时浏览、自制超时期间英文详情读取；不丢作者存储修改、不关闭无关操作、不复活已卸载资料。

### M1｜取消只停后续部分工作

- **核实依据/漏洞处**：`tasks.cancel` 仅 abort；`installOfficial` 在下载文件之前和下载结束检查，解析/发布阶段未贯穿检查；`FileProvider.get/fetchVerified` 没接请求 AbortSignal。冒险取消也不能中断已经发起的取文件请求。
- **方式：漏洞修复**。取消信号传至请求、窗口操作和阶段边界；取消后不发布，保留可复用准备文件。取消完成后才允许卸载，不能只变按钮文字。
- **调用点**：`DownloadTasks.cancel/startOfficial/startAdventure` → `installOfficial` → `FileProvider.get` → `fetchVerified`；发布处再检查操作身份和取消状态，跟 H9 合并生命周期。
- **验收**：请求卡住、解析中、发布前取消；无后台继续覆盖已读版本，无任务 cancelled 但安装已发布的含糊结果。

### M2｜超时没有覆盖完整操作

- **核实依据/漏洞处**：service 的 180 秒只包 `brewAddUrl/brewAddSources` 那次窗口调用；后续 `afterBrewChange` 不在时限内；`brewPull/CheckUpdates/Delete/Import` 无同等整体时限。`runtime/host.ts` 通用 call 结果没有截止时间，只有 ready 有超时。
- **方式：漏洞修复**。整个操作有可观测阶段、截止时间和取消收尾；窗口命令挂起必须拒绝并释放 pending，错误包含阶段。不套一个 Promise.race 后任由后台继续写入，局部关闭参照 H9。
- **调用点**：`service.withTimeout` 与全部修改入口、`runtime/host.ts::call/close`、下载器和后台解析；用户可见重试使用原操作目标。
- **验收**：故意让网络、依赖、解析分别无响应；到时退出该操作，旧版仍可用，重试不出现双写。

### M3｜资料变更后的缓存失效不一致

- **核实依据/漏洞处**：官方任务在 `core/backend.ts` 接换算/配对预热，没有统一 reset service/scoped；普通自制 `afterBrewChange` 只 reset service，不同于 `CustomLibrary.after` 另调 scoped.reset。`EntryLinks.corpusIndex` 成功后一直缓存，直到 reset。前端 `useTags.ts::memo` 还按语言/标签/内容永久缓存结果，既不带资料版本，也不移除 catch 后返回的降级结果，短暂失败可能持续显示错误文字/失效链接。
- **方式：修架构**。发布成功生成一个资料版本变化通知，按依赖更新窗口、定位、类别判断、配对、排序与内核缓存；查询内使用同一代数据。不能靠每个按钮手动补一个 reset，也不能边读取边全局关闭窗口。
- **调用点**：`core/backend.ts` 下载完成路径、`LibraryService.reset/afterBrewChange`、`ScopedLibrary.reset`、`EntryLinks.reset`、`Sorting` 的 generation、配对/结算指纹和 `ui/libview/useTags.ts::resolveTagOnce`；前端这一点须等后端版本通知定好后再批准接线。
- **验收**：先缓存书目定位，再安装/更新/删除自制书，定位立刻反映变化；官方更新后的对象与搜索/配图/英文不混用旧数据。

### M4｜更新漏冒险正文，移除文件未完整回收

- **核实依据/漏洞处**：`OfficialUpdates.check` 比较 `precachePlan`，排除冒险正文；`apply` 不清理统计到的 removed；安装逐条 put 已解析结果，没有按新结果集合替换所有已移除的类别/正文。`scoped.adventures` 用解析记录存在性判断 downloaded，没有核对其版本。
- **方式：漏洞修复**。计划 = 已装目标所需文件（包括已下载冒险）与新版本差异；成功发布时剔除不再属于新集合的文件/解析索引，其他使用者仍需要的共享文件保留。不在开始更新时删除旧版。
- **调用点**：`OfficialUpdates.check/apply`、`precachePlan/adventurePlan`、`installOfficial`、`startAdventure`、`scoped.adventures`、`service.corpus`。
- **验收**：已装冒险只改正文仍检测并更新；移除书/文件后不再读旧解析；未装冒险不因检查更新全部下载。

### M5｜我的库副本不能摆脱整套官方状态

- **核实依据/漏洞处**：P5-1 §0 承诺本地副本不受源卸载影响；`BrewPacks.list` 官方未 installed 返回空，`scoped.installed` 也屏蔽自制；`custom.exportBrew/exportBackup` 依赖作者窗口。原始副本仍在 KV，不能称已永久丢失，但管理/使用受到阻断。
- **方式：修架构**。区分作者启动基础资源与可选官方书，基础资源作为显式依赖保留；本地包头/原文清单与导出不依赖全套官方 installed。副本的 `_copy` 等依赖按作者机制保留/安装/报告，不承诺只复制原文件就一定自足。
- **调用点**：`BrewPacks.list`、`officialInstalled`、`scoped.installed`、`CustomLibrary.saveToMine/exportBrew/exportBackup`、`MyLibTab`、`copyRawSource`。
- **验收**：存副本 → 卸载原书 → 重启断网 → 能列出/导出副本；内容若缺基础依赖需明确列出，不显示“没有资料”。

### M6｜浏览与战役启用混用

- **核实依据/漏洞处**：P5-0 U1/U2 要求浏览和下载不因无战役被挡，关书仍可查看；`loadPackRows` 调 `scoped.query`，该函数 `if (!v.visible) continue`。`off` 标记无法把被后端过滤掉的行变灰显示。`scoped.fetch` 已放行 closed，不等于列表也已放行。
- **方式：修架构**。提供已有本地书/包的只读浏览路径，另带战役启用标记；战役检索/选用继续过滤。复用同一作者对象与版本选择，不在前端临时删除 exclude 模拟。
- **调用点**：`ScopedLibrary.query/detail/fetch`、`loadPackRows`、`PackPage.load`、条目详情、全库浏览与战役选择器；先定义各自用途，不能把所有查询都改成无过滤。
- **验收**：关闭一本书后仍浏览内容且显示关闭；战役选择器不出现它；已有存档直接引用仍可取并带 closed。

### M7｜日志被体检阻断，失败报告被隐藏

- **核实依据/漏洞处**：`LibSettings.vue::loadLogs` 先 await health，再读 logs；`service.health` 某套自制窗口失败直接 reject 整体；`health.ts::healthItemsOf` 对未安装官方提前返回“还没安装”，忽略已有失败报告。
- **方式：漏洞修复**。持久日志先独立读出；体检每来源隔离失败并返回该来源错误；失败安装和从未安装区分，不遮掉 download/mirror/parse 报告。日志导出失败要有可见反馈。
- **调用点**：`service.health` → `healthItemsOf` → `LibSettings.loadLogs/copyAll/exportAll`，底层 `LogStore.list/exportText` 继续只读库。
- **验收**：作者窗口完全开不了仍能查看/导出历史日志；安装失败可见具体阶段；某套失败不遮另一套。整页空白的真机根因仍不能仅凭这条断定。

### M8｜部分失败被当成功、检查错误被过滤

- **核实依据/漏洞处**：`BrewCatalog.download` 仅全部语言失败时向 trackBrew 返回错误，一边失败仍 return null；只读 `res.errors` 不消费 parse 错误。`update-flow.ts::pullUpdates` 将 brewCheckUpdates 的 value 过滤成 hasUpdate，逐包 error 被丢；`import-flow.ts` 只检查 r.errors，不检查 parse/notJson，catch 还笼统声称原内容未改。
- **方式：漏洞修复**。保留每目标/语言的成功、失败、未检查；只重试失败目标；解析与源调用错误均进入统一结果。“没有新版”仅适用于检查成功的包；原件已写入但解析失败时说明实际状态，不谎报回滚。
- **调用点**：`BrewCatalog.download` → `stores/downloads.trackBrew`；`pullUpdates` → `brewCheckUpdates/brewPull`；`importFiles` → `brewImport`；统一结果判定归 H5。
- **验收**：中成功英失败不撤销失败状态；重试不重复安装成功边；一个包检查失败不能显示“全部最新”；混入坏 JSON 不按所选文件数报全部成功。

### M9｜逐条重复读取管理表导致查询慢

- **核实依据/漏洞处**：`ScopedLibrary.query` 循环每条调用 `alternativesOf`，后者每次 `await manage.houseRules()`；版本/归类已有部分批量读取，不能把全部工作都说成逐条读。P5-1 B-44 的约 19.6 秒是历史总耗时，不是本轮计时，也未证明全由房规造成。
- **方式：漏洞修复**。每次查询构建一次管理上下文，将房规按目标编号分组；循环只查内存映射，所需房规对象批量取。先统计读取次数和分项耗时，不以加大缓存或前端边画边等替代。
- **调用点**：`ScopedLibrary.query/alternativesOf/houseUnits/choicesFor`，搜索 expand/detail 同类路径一起核查；`pack-data.loadPackRows`、`search-data.loadAllHits` 是放大调用方。
- **验收**：管理表读取次数不随条目数线性增长；真实作者数据输出保持一致，记录首查/重复查耗时；不在文档虚构新的性能数字。

### L1｜进度/能力记录和验收依据不一致

- **核实依据/漏洞处**：NEXT 既写 P5 又保留“当前 P2”等过期停点；P5 下载 e2e 明确接受一键安装全部。P4-0c 顶部修订/P2 B1 原先确实采用整套离线设计，不能倒写为作者禁止单本下载，也不能捏造历史上从未批准整套方案。
- **方式：文档/验收漏洞修复**。保留历史记录，当前需求以驾驶员本轮要求为准；执行前形成唯一当前接口能力表和验收条件。测试应验证选书行为与失败后不丢可读数据，不能只测现有按钮文字。
- **调用点/位置**：`NEXT.md`、P5-0 §13.6、P5-1、`tests/e2e/library/p5-download-ui.mjs`；本文只记录冲突，不自行修改驾驶员维护的总纲，也不将建议标为已批准。
- **验收**：实现、测试、交接均能回答按书安装、依赖、更新范围和失败恢复；已实现、自动验证、真机验证、驾驶员验收四者分别记录。

### N1｜数据版本记号漏另一套官方资料（复核新增）

- **核实依据/漏洞处**：`library/kernel-check.ts::libraryDataVersion` 遍历所有官方集，但仅在 `if (!official)` 时写入一个提交号；中文在前且已装时，英文提交变化不会写入 `official`。`schemas/kernel.ts::kernelVersionSchema` 当前只有单一 official 字符串和 brews；现有语义不表示所有官方来源的组合。
- **方式：修架构**。版本依赖必须按实际读取的官方集和安装来源集合计算，沿用已有摘要/指纹工具；可以继续用一个字符串保存组合摘要，但必须明确算法版本及旧标记兼容/迁移，不能再取“遇到的第一套”。不要直接改作者条目结构。
- **调用点**：`libraryDataVersion` → `core/backend.ts` 注入的 currentVersion/dataVersion → 内核存档保存/检查、`KernelPrecompute`、运行时缓存指纹；结合 H1/H2/M3 一次统一，避免只修读档提示而漏掉内核缓存。
- **验收**：中不变、英更新；英不变、中更新；只装一种语言；同仓库提交但安装来源集合变化；每种依赖变化都得到可区分版本，旧存档引用不丢。组合摘要相等只说明依赖版本相同，不代替内容无损审计。
