## 0. 一句话目标

把作者完整建卡器（私人完整版 Plutonium）**建卡流程里实际显示的程序界面字**收齐，按出处定好中文，交给**现有的**语言包生成器。生成器把这些字写进**现有的** `vendor/foundry/modules/plutonium/lang/zh.json`，编号规则也沿用现有的。建卡专用小窗本来就在加载这份文件，第 3 段第 4 步的换字出口就按同一个编号来取。

```text
本任务做的（左）                                     本任务不做的（右）
作者建卡器全流程 ──探针收字──▶ 程序界面字清单           建卡小窗里把英文换成中文的出口
        │                         │                   （第 3 段第 4 步，驾驶员另批）
        │         现成来源按顺序给候选（第 3 节）         资料名 / 正文（第 3 段③类，另定）
        ▼                         ▼                   作者程序本身（一个字都不改）
   tools/ 底稿（英文 + 中文 + 出处 + 状态）
        │ npm run gen:kernel-lang（现有生成器，加读底稿）
```

### 3.2 翻译规则

1. **术语统一。** 和本战役中文资料、dnd5e 中文包、大译名表用同一个词：
   - 种族（不用「物种」）、装备（不用「器具」）、职业、子职、专长、法术、背景；
   - 调整值、熟练、属性值、起始装备、法器、戏法、准备法术。
2. **按建卡语境译。** 例如 Next / Previous 译「下一步 / 上一步」（不用中文站的「下一章 / 上一章」）。
3. **标点。** 全角「，。：；？！（）」；省略号写「……」；英文冒号结尾的标签改成全角冒号。
4. **保留原文的东西：**
   - 按键名 SHIFT、CTRL、ALT；
   - UA；
   - 来源缩写，比如 [PHB]；
   - 骰子式，比如 2d4、4d6；
   - 数字和单位缩写（gp）照原样，或者照中文资料的写法（金币）。拿不准就进复核清单。
5. **空位。** 每个 `{}` 都要保留，个数不能变，顺序可以调。底稿里在 `note` 写明每个 {} 填什么。
6. **按钮用短动词**，比如「添加」「重置」「完成建卡」。提示句写完整的一句话。
7. **被按钮隔开的半句**（如 `Alternatively,` / `– or –` / `and skip to the shop.`）：在页面上找出整句的先后，几段放在一起翻，保证连起来读得通。这一类一律进复核清单，附整句截图路径。
8. **不翻的东西：**
   - 资料名、正文；
   - 来源全名（书名属于③类）；
   - 编号；
   - 玩家起的名字；
   - 任何会被作者当成「值」用的字串，比如选项值、设置键。
9. **不臆造规则意思。** 看不懂的提示句先去 Bundle.js 看它用在哪里，还是不确定就进复核清单。

### 3.3 什么时候进复核清单（status: review）

- 序 2 到 4 中两个以上来源给的中文不一样，又不能按 3.2 第 1、2 条定下来；
- 语境不明，比如同一个英文出现在两个意思不同的位置；
- 半句拼接（3.2 第 7 条）；
- 和 zh.json 里已有同编号的译文不一样（见 4.3）；
- 含规则判断或警告意思、agent 拿不准的句子。

已知的一批先放进复核清单：
- `Origin (…)`：中文站有「定制你的出身」，大译名表 origin 是「起源」；
- `Equipment`：中文站「器具」，dnd5e 和译名表都是「装备」，按规则 1 定「装备」，复核清单里写明理由；
- `Mod.`：中文站「调整」，译名表 modifier 是「调整值」；
- `Other`：中文站「其他的」，按按钮写法改成「其他」。

## 4. 第三步：底稿与生成

### 4.1 底稿

位置：`tools/plutonium-ui-translations.json`，提交。字段沿用 `approved-translations.json` 的风格，不另起一套格式：

```json
[
  {
    "lang": "zh",
    "package": "plutonium",
    "text": "Select a {}",
    "translation": "选择{}",
    "from": "agent",
    "status": "final",
    "seen": ["2014:Class", "2024:Origin (Species)"],
    "candidates": [{ "zh": "选择一个{}", "from": "5etools 中文站 js/statgen/…" }],
    "note": "{} = 作者填的类别名（Class / Species …）"
  }
]
```

字段说明：
- `from`：取值 `dnd5e:<语言键>`、`terms:<分类>`、`site:<文件>`、`agent`。
- `status`：取值 `final` 或 `review`。只有 `final` 进 zh.json；`review` 等驾驶员批了，写进 `approved-translations.json`。批过的条目，底稿里保留原样就行，生成时 approved 会覆盖它。
- `candidates`：各来源给的全部说法，供复核。
- 文件只存英文界面短句和中文。**不得**含网址、Patreon / 授权 / 下载相关句子、私人清单内容；收到这类字一律排除，并在报告里写明排除了几条。

生成底稿的脚本：`tools/build-plutonium-ui-draft.mjs`（新）。它的规则：
- 读探针结果和私人版 Bundle.js（只有本机有），算出各来源候选；
- 合并进已有底稿：已有的 `translation`、`status`、`from: agent` 一律不覆盖，只补新行、更新 `seen` 和 `candidates`；
- 本机没有私人版时，提示后退出，不改底稿。

### 4.2 生成器怎么改（`tools/build-kernel-lang.mjs`）

- plutonium 包的输入列表，在现有 `upstream` 之后加上底稿里 `status: final` 的行。编号用同一个 `upstreamKey(text)`。
- 底稿行**直接用底稿的译文**，不再走社区包和大译名表那段自动挑选，因为挑选在底稿阶段已经按语境做过了。`approved-translations` 照旧最先覆盖。
- 生成器**不读**私人版 Bundle.js。只要底稿不变，有没有私人文件夹，生成结果都一样。
- 复核清单 `lang-packs.review.json` 加一段 `pluginUi`，写明：
  - 底稿总数、final 数、review 数；
  - 各 `from` 各多少条；
  - review 行的原文和候选。

### 4.3 编号相同的情况

一个界面字可能和现有 upstream 字串编号相同，比如 `Name`、`Type`。如果两边译文一样，就共用。如果不一样，进 review，不能悄悄覆盖。现有 zh.json 的 232 个键，生成后一个都不能变。

## 6. 禁止

- 不改作者程序（私人版、公开版 Bundle.js 都不改），不做运行时换字，不碰 DOM。换字出口是第 3 段第 4 步，驾驶员另批。
- 不在 `vendor/private/` 放语言文件（会盖掉自带的那份，见第 1 节）。
- 不翻资料名和正文，不改编号、选项值、存档值、玩家起的名字。
- 不另起格式，不另起取字服务，不另写编号函数，不另写译名表读取。
- 不按相似度配对，比如「哪个中文重叠最多就配哪个」。中文站只取同文件同位置的配对。
- 底稿和文档里不出现私人下载链接、清单或授权信息；不提交 `vendor/private/`、`dist/`、`RULE LIST.md`、`docs/任务总纲.md`、`tools/skills/`。
- 如果发现要逐条手写的量远超第 7 节的估计，或者要改后端运行代码，先停下来报告驾驶员。
- 一个任务一个本地提交，只用 main，不推送。

## 9. 交付报告要写什么

用大白话，结果放在最前面，配 ASCII 图。

2. 各来源各多少条，final 多少，review 多少。
3. 复核清单表：原文 / 候选 / 推荐 / 理由；半句拼接附截图的完整路径（截图要亲自看过）。
4. 验收表（第 5 节）：每项通过或不通过，附日志路径。
5. 没做到的、没验证的。
6. 自检：对照 Rule list 写这次犯的根本错误，每条配上以后的应对办法。
