## 5. 标准循环（每个"小批"都走完这 13 步，不许跳）

**小批 = 站文档里的一个"工作项"**（一行清单）。一个工作项一个提交。

| 步 | 做什么 | 怎么算过 |
|---|---|---|
| 1 | 读工作项：问题、修法、条目数、来源、验收、陷阱 | 你能用一句话复述"改哪些条目的哪个字段，从什么到什么，依据什么" |
| 2 | 用 T1 `show` 看 3 个典型条目的现状；用 T3 的完整清单确认条目数与站文档一致 | 条目数一致；不一致 → 停（第 11 节第 3 条） |
| 3 | 选落点：**规则**（第 6 节判据）还是**逐条表** | 写在提交说明里 |
| 4 | 写修正（逐条表行 / 规则文件）**和**对应的放行规则（T5） | 放行规则的 `expect` 数 = 工作项的条目数 |
| 5 | 构建：第 8 节命令，输出存文件 | 退出码 0；日志里"修正表：N 条已应用 / 规则 X：命中 M 个"与预期相等 |
| 6 | 跑**相关**的 `g2*` 测试（工作项里点了名） | **预期会失败**，且失败原因是"登记的发现变了/没复现" |
| 7 | **读失败信息**，确认每一条失败都是"本批目标项按预期变化"；出现任何其它失败 → 停 | 失败项 ⊆ 本批目标项 |
| 8 | `G2_WRITE=1 npx vitest run --config vitest.data.config.ts <这批相关的测试文件>` 重写登记 | 命令成功 |
| 9 | `npx tsx tools/g2/registry-diff.ts --allow "…"`（照抄工作项里的那行） | 退出码 0，且输出的"变化清单"与预期一致 |
| 10 | `npx vitest run --config vitest.data.config.ts tests/data/g2-additive.test.ts tests/data/g2-oldext.test.ts` | 全过 |
| 11 | `npm run check`，再 `npm run test:data` | 全过（耗时见第 8 节） |
| 12 | **抽查 3 条**：用 T1 `show` 看修完的条目，**对照来源原文**，在报告里写"条目 / 字段 / 值 / 来源页码或字段 / 是否一致" | 3 条全一致；写不出来源 = 这批没做完 |
| 13 | 提交（第 9 节）；在站报告里加一小节 | `git status` 干净（构建副产物按第 8 节处理） |

> **为什么第 6 步"预期失败"**：G2 的检查测试把"体检发现"逐项登记，数据一变，登记就对不上。这正是安全网——它把"你到底改了什么"摊开给你看。**不要为了让测试变绿而直接重写登记**；先读失败信息（第 7 步），再重写（第 8 步），再用 T2 核对（第 9 步）。

## 6. 修正的两种落点

### 6.1 选哪种

| | 修正规则（`tools/data/fix/rules/*.ts`） | 逐条修正表（`tools/data/fix/rows/*.ts`） |
|---|---|---|
| 什么时候用 | 同一类问题 **≥ 8 处**，且"哪些条目、改成什么"能由代码从数据本身**确定**（例：126 处法术纯文字名补链接、342 个充能动作、300 条抗性解析、40 个等级列） | **< 8 处**，或每处的新值各不相同需要查书（例：价格、体型、骰式、起始装备） |
| 必须带 | `expectCount`（预期命中条目数）。命中数不等于它，构建失败 | 每行的 `before`（现状）与 `basis`（来源） |
| 禁止 | 用写死的清单决定"哪个条目改成什么值"（那是逐条表的活）；"尽量匹配""模糊匹配"。例外：允许把规则**限定在 ≤ 7 个明确列出的条目 id 上**来钉死范围（站文档会点名） | 单文件 > 60 行（超了拆文件，≤400 行硬限制） |

### 6.2 逐条修正表的格式（T4）

```ts
// tools/data/fix/rows/s2-price.ts
import type { Fix } from '../engine'
export const ROWS: Fix[] = [
  {
    id: 'item.sling-bullet.phb',          // 条目 id，必须唯一匹配到一个条目
    path: '/data/value',                   // JSON 指针，从「条目」根算起（所以是 /data/…；名字、摘要、关键词是 /name、/summary、/keywords/N）
    op: 'set',                             // 'set' | 'delete' | 'insert'
    before: 1,                             // 构建时现状必须深度相等，否则构建失败
    after: 0.2,
    basis: '5etools items 原始价格 0.2 cp；PHB 装备章 投石索弹丸 20 颗 4 cp', // 书名+页，或参考文件+字段
  },
]
```
- `op: 'delete'`：`after` 省略；`before` 必填。
- `op: 'add'`（新增整个条目）：行里写 `pack`（目标包 id）与完整的 `entry`；新条目**必须从同一个包里同类型的一个现有普通条目原样克隆结构**（先用 T1 看一个），只改 id、名字、英文名、摘要、关键词、业务字段与出处页码；id 已存在 = 构建失败；每个新条目还要进 `g2-additive` 的 `ADDED` 清单。
- `op: 'insert'`：`path` 指向**已存在的数组**里的位置（例 `/data/effects/2`；下标 = 数组长度表示追加），`before` 省略，`after` 为要插入的元素；越界、父级不是数组都失败。
- **给对象新增一个原来没有的字段**（例如给某个 `spellGrant` 加 `level`、给 `hp` 加 `special`），或**整个数组原来就不存在**时（例如这个特质原来没有 `effects`）：用 `op: 'set'`，**`before: undefined`**（含义＝"现在没有这个字段"，现状若已有值就失败），`after` 写新值（新数组整个写进去）。
- 引擎行为：找不到条目 / 匹配到多个 / `before` 不等 / 同一 `id+path` 出现两次 / 有某行没被用上 → **构建失败**，并列出行号。
- 引擎在构建日志打印"修正表：N 条已应用"，并把清单写进 `tools/data/out/fix-report.json`。

### 6.3 修正规则的格式（T4）

```ts
// tools/data/fix/rules/s2-spell-links.ts
import type { Rule } from '../engine'
export const RULE: Rule = {
  name: 's2-spell-links',
  expectCount: 126,                        // 预期命中（被改动的）条目数
  apply(packs, ctx) { /* 返回被改动的条目 id 列表；只改本规则负责的字段 */ return [] },
}
```
- 规则要**幂等**（对已修好的数据再跑不再改）、**确定**（不依赖遍历顺序、时间、随机）。
- 每新增一个文件，在 `tools/data/fix/index.ts` 的列表里加**一行**注册。

### 6.4 执行顺序

`cleanEntries`（R14 文字清理）→ **修正规则（按注册顺序）→ 逐条修正表** → 英文对照 → 校验。`before` 比的是**经过 R14 清理、也经过前面规则之后**的值。

## 7. `g2-additive`：逐条放行（T5）

- `g2-before.json.br`（brotli 压缩）= G2 开工时（1.3.0，哈希见 `docs/probes/D1.2-G2_快照.json`）**每个条目的全文**。
- 测试把每个条目与现在的内容做深度对比，得到"变化路径"（如 `/data/value`）。**每个变化路径必须被某条放行规则覆盖**：

```ts
// tests/data/g2-allow/s2.ts
export const ALLOW: Allow[] = [
  { name: 's2-price-decimal', station: 2, ids: [ 'item.sling-bullet.phb', /* …精确列出 */ ], path: /^\/data\/value$/, expect: 11, reason: 'a15-value：价格不取整，一位小数' },
]
```
- `ids` 用**精确的 id 数组**或"类型 + 路径"（`type: 'monster'`）二选一；**不许用宽泛正则匹配 id**。
- `expect` = 该放行规则**实际命中的条目数**；实际数 ≠ `expect` → 失败（防止放行范围悄悄变宽）。
- 新条目（第 3 站会新增约 10 件装备）必须列进 `ADDED`，写明 id 与来源；**删除条目不允许**。
- 名字、英文名、摘要、关键词的变化也算变化，同样要放行。

## 11. 停止条件（命中任何一条：立即停手，不绕过，写报告）

1. **文档矛盾或含糊**：两份文档说法不同，或某句话你有两种读法。
2. **冻结/前置缺失**：第 2 节任一条不满足；或需要改 `src/`、需要新字段/新取值/新记号。
3. **条目数对不上**：T3 完整清单与站文档的条目数不一致；或规则命中数 ≠ `expectCount`；或逐条表 `before` 不符。
4. **registry-diff 不过**：出现 `--allow` 之外的变化，或出现**新发现**；本批目标项没降到预期数量。
5. **g2-additive 失败**且你解释不了（"我也不知道为什么这个条目变了"）。
6. **旧扩展 0.2.0 装不上新包**（`g2-oldext` 失败）。
7. **来源矛盾**：书、5e API、Foundry、5etools 之间互相矛盾，判断不了以谁为准（以谁为准的规则：见 02/03 各项的"来源"列；列里没写的，停）。
8. **要改已有字段的含义**，或波及的条目比放行规则多。
9. **某项拿不准要不要结构化**（旧清单第 1 章原则 4）：做预览交驾驶员，不自行判定"不做"。
10. **钉死数字测试**因与你工作项无关的原因失败（第 3 节第 16 条）。
11. **两次构建哈希不同**。
12. **同一个问题你尝试修了 3 次仍不过**：停，写清三次各做了什么、各看到什么。
13. 你发现自己想做以下任何一件事：改测试期望让它变绿；放宽放行范围；"先改了再说"；手改生成物；凭记忆填数值。**这就是该停的信号。**

**怎么停**：不再改任何文件；在聊天里用大白话报告："停在哪一站哪个工作项 / 命中哪一条停止条件 / 我看到了什么（贴命令输出）/ 我的推测（标明是推测）/ 需要你决定什么"。已经做完且通过全部 13 步的工作项保留提交；做了一半的用 `git checkout -- <你改的具体文件>` 回退到上一个提交。

## 12. 常见走偏（上一轮 62 张卡的复盘，逐条对号入座）

1. **"有这个字段"≠"数据真的流到用户面前"**。改完字段要在**构建产出的包**里用 T1 看到它，并且读取器测试能读到。只在转换代码里写了、没出现在包里 = 没做。
2. **自指夹具**：用"数据自己"当期望值，或用 5etools 核对 5etools 导入的内容，测试永远绿。期望值必须来自独立来源（原书、5e API、Foundry），或来自站文档给定的值。
3. **"有闸门"≠"闸门盖得住"**：`g2-additive` 的放行规则写得太宽，等于没有闸门。`expect` 数必须精确。
4. **只看数量不看内容**：登记数量降到 0 不等于改对了。第 12 步的"抽查对照来源"不能省。
5. **顺手修**：看到旁边也有问题就一起改了。串批后，T2 会拦住——但你应该根本不去碰。
6. **静默兜底**：写 `?? 0`、`catch {}`、"找不到就跳过"。找不到就应该**失败**（引擎就是这么设计的）。
7. **规则写得"聪明"**：用模糊匹配、猜测、LLM 式的自然语言解析。规则必须笨、窄、确定；判断不了的留给逐条表。
8. **UI 层问题只有人能抓**：你看不到界面，所以**不要宣称"显示正常"**。报告里写"数据已按规格产出；界面未看"。
9. **改了一个类的一个例子**：同类问题（如所有"1环/6th"写法）要按规则整类修，并确认整类清零，而不是只修登记里列出的前 50 个。
10. **报告里写"应该没问题"**：不允许。写"已验证：命令+结果"或"未验证"。

## 13. 名词（大白话）

| 词 | 意思 |
|---|---|
| 包 / `.trpgpack` | 一本书的数据压缩包；共 11 个（SRD + 10 本书） |
| 条目 | 包里的一条数据（一个法术、一个种族、一个怪物……），有唯一 `id` |
| 登记表 | G2 体检时记录的"发现"，每个发现有编号、条目数、前 50 个条目 |
| 登记项 / 发现 | 登记表里的一行，如 `a17-spelling` |
| 修正表 | 一行行写明"哪个条目的哪个字段，从什么改成什么，依据是什么" |
| 修正规则 | 一小段代码，按固定条件批量改同一类问题 |
| 放行名单 | `g2-additive` 里写明"允许哪些条目的哪些路径变化"的清单 |
| 冻结 | 第 0 站做完、驾驶员签字之后，字段形状不再改 |
| 驾驶员 | 项目负责人（用户），只有他能验收、能授权推送 |

## 14. 2026-11-01 重排：根因分流与先找数据源（规划者与执行 agent 都要遵守）
