## 1. 要做成什么样

```
现在                                  做完
怪物表单                              怪物表单
  swarmSize        [   ]               集群体型      [   ]
  immune           [ ▾ ]               伤害免疫      [ ▾ ]
  conditionImmune  [ ▾ ]               状态免疫      [ ▾ ]
  动作 ▸ 中文名    [   ]   ← 错         动作 ▸ 名称   [   ]
  senseTags        [ ▾ ]               感官标签 ⓘ   [ ▾ ]   ⓘ = 一句提示：「筛选用，……」
```

- 字段名：表单里每个用户看得到的字段尽量是中文。
- 一句提示：只给「必填」和「常用」两块里的字段（字段旁 ⓘ），「更多」里的不强求。
- 中文栏用中文名；英文栏不变（继续显示作者原字段名，`rawNames`）。
- **不做**：条目内容（正文、名字）翻译；下拉选项的显示名已由 C10 从作者 `Parser` 对照表接通（`src/library/field-values.ts`），这次只补它没覆盖到的（见 §4.4）。

## 4. 对换规则

### 4.1 流程

```
 结构定义里的全部字段（vendor/brew-schema/fields.js，按类别 + 路径）
        │  去掉 internal（Foundry 等）、publish（出版信息）、自动字段（第 1 步 autoFields）
        ▼
 ① 已有作者标签（A）有 → 用
        │ 没有
        ▼
 ② 字段名拆成英文说法：conditionImmune → "condition immune"
    在 B + C 里整句查（含单复数：+s / 去 s / +es）→ 查到 → 用，标「术语表」
        │ 没有
        ▼
 ③ 逐词查，全部查到 → 拼起来，标「逐词拼，待抽查」
        │ 还有词查不到
        ▼
 ④ 进「手译清单」：只译 §5 范围内的；其余保持英文，不算失败
```

①–③ 全部写进生成工具（扩展 `tools/build-field-labels.mjs`），可以重跑；④ 才写进手译文件。**不允许把 ①–③ 查出来的结果手抄进手译文件。**

### 4.2 术语表（C）怎么挑

- 只用这些分类：空分类、`variantrule`（规则术语）、`normal`（常规翻译）、`other`、`bestiary`（怪物页的数据栏标题，如生命值、巢穴动作）、`creature`、`language`、`itemMastery`。
- **排除**专名类：`spell`、`area`、`name`、`deity`、`book`、`adventure`、`group`、`plane`、`card`、`psionic`、`vehicle`、`object`、`race`、`class`、`feat`、`item`。实测不排除会出错：Fly → 飞行术（法术名）、Resistance → 抵抗术（法术名）。
- 只用「已确定」的（`to_be_discussed = 0`；现在只有 1 条待讨论）。
- 同一个英文有几种中文：取分类优先级最高的；还平手就列进「冲突清单」给驾驶员定，不自己挑。
- **撞义要人看**：同一个中文对着两个不同字段（实测 Recharge 和 Charges 都查成「充能」）→ 列进「冲突清单」。
- 作者编辑器标签（A）和术语表结果不一样时，A 优先（作者在表单里就是这么叫的；例 `level` 法术叫「环节」、怪物叫「等级」，这是按类别分开的）。

### 4.3 按位置（层级）给名字

- 同一个字段名在不同位置意思不同时，按「类别 + 路径」分别给：顶层 `name` = 中文名，`action[].name` = 名称（作者界面词表 `common.name` = 名称）。
- 路径写法沿用第 2 步表单安排的（`field`、`.sub`、`[]`、`{}`）。
- 现有共用表里硬套到所有层级的（`name`、`any`、`or`、`type`、`source`…）逐个核对，错的改成按位置给。

### 4.4 选项值（补 C10 没覆盖的）

- 先统计：表单里有选项、但 C10 没给显示名的位置有多少（`field-values.ts` 拿不到表的那些）。
- 值是另一种条目的名字（状态、感官、语言、技能、伤害类型…）：用 E 的转换函数或 D 的 `ENG_name` 对换；还是不行再查 C。
- 小窗里调作者函数，和 C10 同一个入口（`valueLabels` 旁边加），不在界面里转。

## 5. 一句提示和手译的范围

- **一句提示**只给出现在任一类别「必填」或「常用」块里的字段（`custom.formPlan` 的 `required` + `common`）。
- 提示从作者结构定义的英文 `description` 翻（有的字段没有，例如 `ac`、`immune` 实测都没有）；没有就按字段用途写一句，越短越好。
- **手译字段名**同样只限必填 + 常用；「更多」里查不到的保持英文。
- 以下必须有提示（之前几步记下的）：
  - `senseTags`（感官标签）：作者转换器解析文字时写的，**筛选用**，不影响正文显示；第 1 步认不出它是自动字段，所以留在表单里。
  - 独立表的 `rows` / `tables`：两种写法二选一（第 3 步已改成只要求当前那种）。
  - 职业表 `rowsSpellProgression`：每一格是数字（法术位个数）。
- 手译完先给驾驶员抽查，再提交。

## 6. 存在哪、谁合并

```
tools/build-field-labels.mjs   （扩展：读 A + B + C + 结构定义，按 §4 生成）
        │ npm run gen:field-labels
        ▼
vendor/brew-schema/field-labels.js   自动生成，不手改
   byProp   按类别：字段 / 路径 → { 中文名, 来自哪里 }
   shared   按路径共用的
   review   冲突清单、逐词拼的（给驾驶员抽查，不进界面）

src/library/field-labels.json        只放手译（§4.1 第 ④ 步），同样按类别 + 路径，可带一句提示

formats.ts fields()                  合并：作者编辑器 > 生成的 > 手译；都没有就不给（界面显示英文）
```

- 术语表 C 有 15 MB，**不进仓库**。生成工具从命令行参数或默认路径读它，把文件名（含日期版本）写进生成结果的 `generatedFrom`；作者更新了术语表就换文件重跑。
- 还是同一套字段表、同一个合并入口，**不另起一套结构**；手译文件的格式在预览里给驾驶员看过再定。
