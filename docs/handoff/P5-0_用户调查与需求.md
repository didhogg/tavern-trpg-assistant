## 4. 按显示区分的数据类型（S2 定稿草案，2026-11-09）

按 S1 的答案调整：包/书内是**一个混合列表**，类别是筛选项；条目页**一个页签**（正文 + 背景）；图片、表格在嵌入位置做成下划线条目，点开才显示；所有类别共用同一种术语跳转。下面的"组"只用来决定**详情怎么显示**，不再决定列表怎么分页。

### 4.1 数据口径与核对范围

| 范围 | 怎么核的 | 结论 |
|---|---|---|
| 中文官方（2.39.0-cn.3） | 插件自己下载解析后的真实库，一次性只读统计 | 77 个解析类别，其中有条目的 65 个（本节条数来源） |
| **英文官方**（本轮补核） | 同上，同一个旧测试资料夹（中英官方都装好，英文提交 `8790755`） | **同样 77 个类别、同样形状**：75 个类别条数完全相同；差别只有 ① 条数：`item` 中 6600 / 英 6603、`raceFeature` 1661 / 1662（中文数据本身一条之差，B2-8a 已记）；② 字段：**中文多 `ENG_name`（所有类别）与 `translator`（部分类别：法术、种族、背景、专长、可选特性、神祇、变体规则、动作、物件、陷阱、载具、状态、技能、感官、据点）**，英文没有。界面不需要为英文另设计一套 |
| **自制**（官方自制仓库 + 本地导入 + 自己写的"我的资料 / 我的房规"） | 读作者的结构定义 `report/作者的schema/brew/homebrew.json`（114 个顶层属性）；**没有实测**（旧资料夹里没有装着自制，P3-1 那个资料夹里自制已被清掉） | ① 自制能带的**浏览类别**和官方是同一批：`spell / monster / item / class / subclass / race / background / feat …`；② 自制里的 `baseitem / itemGroup / magicvariant / itemType` 解析后同官方并进 `item`，`subrace` 并进 `race`；③ **自制才有**：`book / bookData / adventure / adventureData`（自制里的书和冒险；插件 B2-7 没接，S1 对照表 S1-05）、`encounter`、`name`（名字表）、`citation`；④ **辅助数据不浏览**：`foundry*`、`roll20Spell`、`makebrewCreature*`、`monsterfeatures`、`spellList`、`linkedLootTables`、`blocklist`、`reducedItem*`；⑤ 解析后会多出 `raceFeature`、`tableGroup`（作者生成）；官方的 `monsterTemplate`、`legendaryGroupTemplate` 自制没列；⑥ 每个自制包带 `_meta`（来源全称、作者、版本、网址、发布日期、依赖 `dependencies`、`includes`），`service.brewInstalled()` 原样给出。**解析后字段是否和官方完全同形，没有实测，S3 装一个官方自制样本核对** |

### 4.2 解析后和原始文件不一样的地方（界面只认解析后）

```
 基础物品 + 物品组 + 魔法变体 → 并进"物品"（6600 条，带 _category）
 亚种 → 并进父种族（361 条）；种族特性另出 1661 条 raceFeature
 书和冒险里的表（以及职业等里标了 tableInclude 的表）→ 作者提成"随机表"（2390 条）
 法术多出 classes / feats / rewards / races …；职业、子职业的特性已按等级展开

 itemType / baseitem / itemGroup / magicvariant / subrace：解析后不再是独立条目
```

### 4.4 共用件（所有类别只设计一次）

```
 · 列表：包/书内一个混合列表 + 类别筛选 + 文字匹配 + 排序；全库搜索是悬浮窗口（筛类别 + 文字匹配）；
        表格自适应页面宽度，上下拉伸
 · 条目页：一个页签（正文 + 背景）；右上 En / 中文 快速切换，全局生效；小铅笔进编辑
 · 正文渲染：Vue 渲染器按作者结构定义 entry.json 的 47 种块做"类型 → 组件"登记表
 · 嵌入的图片、表格：显示成下划线条目，点开才是完整表格 / 才拉取并显示图片（缓存放浏览器）
 · 术语跳转：所有类别同一种方式——点击直接换成目标条目；返回回到上一个条目；跨包（只要装了）
 · 骰子标签：点了进骰盘（只接入口）
 · 备选 / 覆盖：在相应位置显示备选，能选用、能解除覆盖；官方条目被房规覆盖时显示【复原】
 · 摘要行（每类 2–6 个小字段）、来源与版本徽章（2014 / 2024、SRD、重印）、被屏蔽 / 本战役不可见标记
```

### 8.5 编辑功能优化建议（你让我帮忙优化；以下是建议，未批准）

先分清你说的两个场景，它们改的不是同一种东西：

```
 场景① 改条目本身的设定（房规）           场景② 游玩中改 次数 / 数量 / 资源
 改的是"库里的条目"                        改的是"这个人物 / 这件物品现在的状态"
 例：火球术改成 10d6                       例：魔杖剩 3 次、药水剩 2 瓶、法术位用掉 1 个
 存哪：房规（备选），原件不动，可复原       存哪：存档里的人物 / 物品状态
 后端：custom.createHouseRule 等（已有）    后端：结算内核的预览→确认→写入→撤销（P3，已有）
 界面：条目页小铅笔                         界面：人物页 / 物品栏（P6）里直接改
```

建议：

1. 库里的编辑界面**只做场景①**。场景②放进人物 / 物品栏（P6）。理由：库条目改了会影响所有引用它的人物与存档；游玩中临时改个数量不该改库，而且要能撤销、要进存档日志。两种混在一个界面里，用户会把"临时用掉一次"改成"永久改了条目"。
2. 场景①再分三档，由浅到深，对应三个入口：
   - **改几个字段**（推荐默认）：用作者的 `_copy + _mod`，只记录改动，原件更新时房规还能跟着走。
   - **整条编辑**：把条目复制一份整体改。
   - **JSON 入口**（高级）：直接编辑 / 替换 JSON；语法错误前端拒绝并指出位置；结构错误等 S3 核对能不能校验（S1-29）。
3. 每一档都显示【复原】（选回原件），原件永远不改；纯自建的条目没有原件，所以没有【复原】，只有"删除"。
4. 保存前给一个小预览："这次改了哪几个字段"，保存后在条目页显示"此条已被房规覆盖（生效处：本战役）"，点它能解除。
