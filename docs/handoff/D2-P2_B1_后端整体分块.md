## 0. 一页结论

```
 设计方式：先定"总骨架"（本文件），再按开发顺序"逐块细化"
           → 现在只细化 ④【库】；⑤ 结算内核在 P3（与【库】关联的后端模块）；其余块到各自阶段再细化

 照抄谁：  ④【库】     → 5etools 作者网站自己的后端（取数、包管理、依赖、屏蔽、搜索、筛选；排版器留给界面阶段用）
           ⑤ 结算内核  → Plutonium（作者的 Foundry 插件）+ Foundry dnd5e 系统的算法（照着移植）
           ⑥ 战役存档  → 保留已做好的 M1（和数据格式无关）
           不抄：Open5e、5e-srd-api、Mimir 等（各有自己的数据格式，抄了就是第二套格式）

 全插件一条铁律：条目只认"作者编号"，条目内容只认"作者加载器展开后的对象"
                 → 插件里不再有任何自定义的条目格式
```

## 1. 为什么"先骨架、后逐块"

```
 ✘ 一次性把 10 块全部细化   → 战斗、地图、给 AI 现在细化是越界，到时候一定返工
 ✘ 完全逐块、没有骨架       → 块与块怎么交接没人管，各自又长出一套格式（旧项目的死循环起点）
 ✔ 先骨架（本文件）再逐块细化
    骨架只定三件事：① 每块管什么   ② 块之间交接什么（第 4 节）   ③ 每块抄谁
```

## 4. 块与块之间的交接规矩（骨架的核心）

### 4.1 条目编号：全插件只用作者编号

```
 作者编号 ＝ 作者程序 UrlUtil.URL_TO_HASH_BUILDER 生成的编号
   普通条目      名字|来源              例 fireball_xphb
   职业特性      名字|职业|职业来源|等级
   子职业特性    再多 子职业简称|子职业来源|来源
   神祇          名字|万神殿|来源
 → 人物、存档、战斗、地图、给 AI 引用条目时，一律存这个编号
 → 插件不再自造编号规则（旧规则"只允许小写字母、数字、点、短横线"作废）
```

### 4.2 条目内容：只有【库】能给，而且只给"作者展开后的对象"

```
 别的块要条目 ──► 问 ④【库】（按作者编号） ──► 拿到作者加载器展开后的对象（只读）
 ✘ 不许别的块自己读原始文件
 ✘ 不许把条目内容复制进人物、存档（只存编号）
 ✘ 不许给条目定义"我们自己的形状"（Zod 结构、统一格式之类）
```

### 4.3 人物、战役、存档只存三样东西

```
 ① 引用：用了哪些条目（作者编号）
 ② 选择：在条目给的可选项里选了什么（例：能力值 +2 加在力量）
 ③ 状态：几级、当前 HP、剩余法术位、身上的状态
 → 条目一更新，人物看到的就是新内容；人物数据里没有"过期副本"
```

### 4.4 结算：纯计算

```
 作者条目（只读） + 人物记录（引用 + 选择 + 状态） ──► ⑤ 结算内核 ──► 结果
 数值优先读数据（例：职业表、兼职法术位表都在作者数据里），算法步骤才照 Plutonium/dnd5e 移植
 同一件事的多种写法按"写法登记表"处理；没登记的写法 → 显示原文 + 自动记进"未支持写法清单"
```

### 4.5 依赖方向（只能从下往上用，不能反过来）

```
   ⑥⑦⑧⑨⑩  游戏层
       │ 用
       ▼
   ⑤ 结算内核
       │ 用
       ▼
   ④【库】
       │ 用
       ▼
   ①②③ 基础层

 ✘ ④【库】不许知道人物、战斗的存在
 ✘ ⑤ 结算不许直接读数据库，只接收 ④ 交给它的条目
```

### 4.6 其他沿用的规矩（来自 `AGENTS.md`、`docs/开发规范.md`）

- 状态只经 store；规则是纯函数；结构变更必带迁移。
- 数据形状归上游：后端只写"数据怎么处理"，**不定义数据应该是什么形状**。
- 后端声明式＋登记式：加一个源、一种写法 = 加一行登记，不改调用方；不写死书目、条数。
- 作者的工具跑不通时：停手，按 `SELF CHECK.md` 自查，向驾驶员报告，**确认后才能手写**。
