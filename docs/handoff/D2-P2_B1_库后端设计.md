## 0. 一页结论

```
 【库】= 作者网站后端 原样搬进插件 + 三件插件自己写的事

 作者已有、直接用（L1 L3–L11 的核心）：
   书目、包管理（装、删、导入、依赖、更新）、屏蔽表（按书开关）、迁移器、加载器、
   预生成的搜索索引、筛选、中英对照、编号规则、体检诊断（排版器也有，留给界面阶段用）

 插件从零写的只有三件：
   ① 官方原始文件的本地存储 + 下载队列（作者网站的数据本来就在服务器上，不需要这个）
   ② 插件 ⇄ 隔离小窗的传话通道（作者的接管写法有现成先例，传话本身要写）
   ③ 旧格式退役（删掉 .trpgpack 那一套）

 官方数据的下载方式：照抄作者自己的离线设计
   除冒险正文外的全部数据 + 搜索索引 一次装好（中文约 68MB + 约 9MB），
   冒险正文按本下载，书的开关用作者的屏蔽表

 解析方式：安装后"全量解析"一次
   按作者自己的类别登记表循环，每一类都调作者加载器这同一个入口；书和冒险按作者书目逐本取
   → 结果存成派生物（可删可重算，原始文件仍是唯一源头）

 存在哪：【库】专用的独立数据库 tavern-trpg-library（4 张表），
         替换旧【库】的 4 张表；战役、人物、存档所在的数据库不放【库】内容

 本阶段只做后端：交出"数据接口"（给条件 → 返回作者对象 / 作者编号）
   列表页、详情页、排版、链接跳转、搜索框、筛选面板、分页 → 全部归 UX/UI 阶段

 怎么证明无损：五层审计（第 11 节）
   ① 本地文件 = 云端镜像   ② 解析全部成功   ③ 原始的每一条解析后都在
   ④ 原始 vs 解析后只有解析处不同   ⑤ 作者搜索索引对账（辅助）
   差异只列清单、查根因，不手写补、不逐条核对书
```

## 1. 目标与边界

驾驶员确认的目标：

```
 打开【库】→ 看到上游书目 → 下载 → 作者的程序（随插件）从云端取数并解析 → 存在本地
 → 能浏览、阅读、搜索、筛选、管理自制 → 重启、断网后还在
```

| 作者负责 | 插件负责 |
|---|---|
| 数据长什么样、怎么展开、怎么排版、怎么配中英 | 取、存、调用作者的程序、管理、交给界面 |

**后端和界面的分界**（本文件只管左边）：

| 后端（阶段 B） | 界面（阶段 UX / UI） |
|---|---|
| 下载、存储、安装卸载、导入、依赖、更新、全量解析、审计、体检 | 扩展包列表页、包详情页 |
| 查询：按类别、来源、编号返回作者对象 | 条目列表页（显示哪几列、分页、排序） |
| 详情：返回一条作者对象 + 背景描述 + 英文对象 | 条目详情页（排版、正文里的链接跳转） |
| 搜索、筛选：关键词或条件 → 作者编号 | 搜索框、筛选面板 |

**不做**：
- 不把数据转成任何自定义格式
- 不手写书单、条数
- 不逐条修数据
- 不定义条目形状

```
┌────────────────── 中文套 ──────────────────┐   ┌────────────────── 英文套 ──────────────────┐

│           （= homebrew.kiwee.top）          │   │                                             │

已核实的事实：
- 中文仓库里的 `data-bak/` 与作者本人 v2.39.0 的 `data/` 抽查 5 个文件，指纹逐个相同。英文套直接取作者本人仓库。

- 中文站程序里，中文自制的地址本来就是 `homebrew.kiwee.top`（`js/utils.js` 第 61 行）。英文作者程序里是 GitHub 上的 `TheGiddyLimit/homebrew`（第 60 行）。
- 中文数据本身就含 2014 版：PHB、DMG、MM 都在书目里，法师有 PHB 和 XPHB 两条。**2014 独立站不接。**
- 以下下载地址都能访问，且允许插件跨站读取（CORS `*`）：jsDelivr（两个官方仓库）、`homebrew.kiwee.top`、`5e.kiwee.top`、`raw.githubusercontent.com`。
- 中文站程序和英文 2.40.0 程序约有 290 处文件差异。中文程序有 53 个文件用到 `ENG_name`。所以每套数据只用自己那套程序读。

### 3.2 源登记表（声明式，加源 = 加一行）

每个源登记这些项：

| 项 | 例（官方中文） |
|---|---|
| 编号 | `cn-official` |
| 种类 | 官方 / 自制 |
| 语言 | 中文 |
| 仓库与锁定的提交 | `tjliqy/5etools-cn@<提交>` |
| 下载地址（按顺序换） | jsDelivr 锁版本地址 → `5e.kiwee.top` → GitHub 原地址 |
| 用哪套作者程序 | `vendor/5etools-cn@<提交>` |
| 配对的另一种语言 | `en-official` |
| 文件清单与指纹（镜像比对的标准答案） | GitHub 目录树接口（锁定版本：每个文件的路径、大小、指纹） |

**下载地址与文件清单分开取（2026-11-06 实测）**：
- jsDelivr 只当下载地址。它拒绝列出超过 50MB 的仓库的文件清单，但单个文件照常能取（实测 3 个大文件都返回 200）。
- 文件清单从 GitHub 目录树取。实测英文 v2.39.0 的 `data/` 有 520 个文件，中文仓库共 2,853 个文件，两份清单都完整、没被截断。

**版本规则**：官方数据的提交，永远等于插件里那套作者程序的提交。所以官方数据升级跟着插件升级走。自制不受这条限制，用作者包管理器的更新功能（L7）。

## 4. "包"是什么

不再有 `.trpgpack`。"包"直接用作者自己的单位：

| 包的种类 | 是什么 | 管理记录在哪 |
|---|---|---|

| 本地自制包 | 用户自己导入的 JSON 文件 | 同上（是否本地 = 是） |

## 7. 三件横跨的事

### A. 小窗与传话

```
 小窗启动
   ① 按作者页面里的顺序加载 20 个核心脚本（含 hist.js；顺序由 B 的工具从作者页面读出）
   ② 照 PatchLoadJson 的写法接管取数出口：
        作者要 data/xxx.json
          → 传话问插件 → 本地仓有就给
          → 没有：若在"安装"中，取件员去云端取、存、再给；否则回答"没有这个文件"
   ③ 照 StorageUtilMemory 的写法接管存储口子：
        作者包管理器、屏蔽表要存东西 → 传话 → 插件存进本地仓 kv 表
   ④ Renderer.setBaseUrl 设成源登记表里的云端地址（地址怎么拼交给作者）
   ⑤ 启动包管理器、屏蔽表、加载器

 传话内容（插件 → 小窗）：展开某类 / 按编号取一条 / 搜索 / 筛选 /
                          装自制（网址或文件）/ 删自制 / 更新自制 / 开关某本书 / 取英文编号
 传话内容（小窗 → 插件）：要文件 / 存取 kv / 报错与诊断
```

### B. 作者程序进插件：`tools/vendor-author-code.mjs`

```
 按源登记表 → 把两套作者程序的 js/、lib/ 原样拷进 vendor/<套名>@<提交>/
           → 用作者的 find-mergable-scripts.js 查出各页面共用哪些脚本；
             加载顺序取作者页面里 <script> 标签的先后（不手抄名单）
           → 记下每个文件的指纹
 体积：每套约 9MB（中文 js 6.2MB + lib 2.8MB）
```

这是插件的构建工具，不碰数据，不含字段名。运行作者的 `find-mergable-scripts.js` 需要驾驶员同意：之前自动审查拦过一次，理由是"运行外部代码"。

   → 源登记表 → 下载各源的目录文件（L1）→ 存本地仓
   → 书目数据交给界面：官方数据集（未下载）、各本书、各自制包
```

### 8.2 下载官方数据集（照抄作者离线设计）

```
 点"下载中文官方数据"
   ① 空间检查：照作者做法，申请持久存储、估算剩余空间，不够就提示
   ② 预载：除 data/adventure/ 外的全部 data/ + search/
        → 中文约 68MB + 约 9MB；文件清单按作者 build-sw.mjs 的规则得出（不手写）
   ③ 下载队列：一个一个取，断了能续，地址按源登记表顺序换
   ④ 每个文件：原样存进 files 表，记指纹
   ⑤ 全部到齐 → 进入第 8.2.1 节"全量解析 + 审计"
   ⑥ 解析完成 → sets 表记"已装，版本 = xxx"，附审计结果
   ⑦ 英文可选：同样流程（约 67MB + 搜索索引）
 冒险正文：在书目里点某本冒险时才下载这一本（49MB 总量，按本取），下载后解析这一本
```

### 8.2.1 全量解析 + 审计（"调用作者全部解析工具，一次解析好"）

```
 作者的解析入口只有一个：加载器 DataLoader（背后 66 个分类加载器由作者自己调度）
 作者的类别清单是作者登记好的：加载器的类别登记表（42 个类别，含背景描述 fluff 类）
                               + 作者书目 books.json / adventures.json

 循环一（整类）：for 每个类别 in 作者的类别登记表 → 加载器.取整站这一类（pCacheAndGetAllSite）
 循环二（按本）：for 每本书/冒险 in 作者书目     → 加载器.按本取（pCacheAndGetHash）
                 （书和冒险整类取会报错，S1 已见；单本入口 B0 已取到 XPHB 正文）

 加载器要什么文件 → 经传话从本地仓拿（不需要知道每个加载器读哪个文件）

 产出：
   ├─► 解析结果：按类别存进 derived 表（带指纹：数据版本 + 已装自制 + 屏蔽表）
   └─► 第 11 节审计的第 1、2、5 层当场跑完，结果进体检
       （第 3、4 层在验证程序里跑，见第 11 节）

 S1 在 Node 里跑过循环一：42 类中 36 类直接成功（每类 0～0.3 秒），
 2 类 0 条，4 类（书和冒险一族）失败 → 由循环二按本取补上

 什么时候重跑：装/删/更新自制、开关书、官方升级之后（指纹变了就重算）
 —— 作者网站的做法也是"改了自制就刷新整页、重新加载"
```

### 8.3 按书开关（"安装 / 卸载"一本书）

```
 关掉某本书 → 屏蔽表加一条"*__*__来源" → 作者的列表、搜索、加载自动隐藏它
 打开       → 删掉这一条
 不删文件：多本书共用文件（职业文件按职业分，一个文件里有各本书的子职业；
           物品在一个大文件里），没法按书删，也不需要删
```

### 8.4 装远程自制包

```
 书目里选一个自制文件
   → 小窗里调用 pAddBrewFromUrl（地址经取数出口取）
   → 作者自动追装它声明的依赖（L5）
   → 作者迁移器处理旧写法 → 存进 BrewDoc（经存储口子进本地仓）
   → 作者标"需要刷新" → 插件重开小窗 → 重跑全量解析，新内容进入解析结果和搜索
 删除：pDeleteBrews → 同样重开小窗
 更新：pPullAllBrews → 列出有新版的 → 驾驶员确认 → 更新
```

### 8.5 导入本地自制包

```
 选文件 → pAddBrewsFromFiles → 作者迁移器 → 存进 BrewDoc（是否本地 = 是）→ 重开小窗
 作者报错 → 原样显示错误，不替用户修数据
```

### 8.6 查询、详情、搜索、筛选（只给数据）

```
 查询：按类别、来源 → 从全量解析结果取作者对象（只含未屏蔽的来源）
 详情：按作者编号 → 作者对象 + 背景描述（fluff，加载器按同名同来源关联）+ 英文对象（8.7）
 搜索：关键词（中文或英文）→ 作者预生成的索引 + 自制现场建的索引 → 作者编号列表
 筛选：条件 → 作者 PageFilter → 作者编号列表（能否脱离网页单独用，B2 先验证）
 ▲ 全部只返回数据。列表怎么显示、详情怎么排版、链接怎么跳、搜索框和筛选面板长什么样，
   都在 UX/UI 阶段按数据形状定，后端不规定
```

### 8.7 看英文原文

```
 中文条目 → URL_TO_ENG_HASH_BUILDER 算出英文编号 → 英文小窗 pCacheAndGet 取出英文对象
 没有英文名的条目 → 用 getEnglishEntity 的定位方法（同数组同位置、同来源同页码）
 取不到 → 返回"无英文对照"，并自动进体检清单
```

### 8.8 断网、重启

```
 重启 → 小窗启动 → 作者要的每个文件都从本地仓拿 → 与在线时完全一样
 B0 已证明：存进去、断网重开、读出来，指纹一致（Chrome、WebKit）
```

## 10. 本地仓：独立的库数据库，替换旧【库】的表

### 10.1 新旧对照

旧【库】存的不是作者原始数据，而是转换后的数据：作者数据 → 手写转换器 → `.trpgpack` → `entries` 表。旧表是按第二套 schema 建的，所以不能沿用，只能换掉。

```
 现在                                     换完以后
 ┌─ tavern-trpg-assistant ───────┐        ┌─ tavern-trpg-assistant（用户数据：小，丢不得）─┐
 │ packs       旧包清单          │  删掉  │ workspaces  战役、人物                          │
 │ entries     我们格式的条目    │ ─────► │ saves       存档                                │
 │ searchIndex 我们建的搜索索引  │        │ blobs       图片仓库（人物头像、导出导入在用，  │
 │ packTrash   旧包回收站        │        │             不是【库】专用，保留）              │
 │ workspaces / saves /          │        │ meta        设置                                │
 │ blobs / meta                  │        └─────────────────────────────────────────────────┘
 └───────────────────────────────┘        ┌─ tavern-trpg-library（新：【库】专用）──────────┐
                                          │ files / kv / sets / derived（见 10.2）          │
                                          └─────────────────────────────────────────────────┘
```

**为什么单独放一个库数据库：**

| 理由 | 说明 |
|---|---|
| 两类数据性质完全不同 | 【库】约 150MB，坏了能重新下载；战役、人物很小，丢了就没了 |
| 互不牵连 | 清空或重建【库】时，碰不到战役和存档 |
| 升级互不影响 | 【库】的表要改时，不用动用户数据库的结构版本 |
| 作者的思路也是这样 | 作者网站把离线数据和用户的自制内容分开存 |

"结构升级迁移"指的是：数据库每改一次表，结构版本号加 1，并登记新表。已经装过插件的用户打开后会自动升级，老数据原样保留。迁移本身不转换任何数据。

### 10.2 四张表

```
 files    官方原始文件     套名 + 路径 + 提交 → 原文 + 指纹        内容（上游的，只读）
 kv       作者存储口子     键 → 值（自制包 BrewDoc、屏蔽表等）     作者自己的存储，原样
 sets     官方数据集记录   套名 → 版本、状态、下载进度、占用空间   插件的管理记录
 derived  派生物           全量解析结果（按类别）、审计报告；      派生（可重算）
                           带指纹，变了就重算，可删
```

插件只存作者对象**整个原样**，不挑字段、不改名、不重新组装。读的地方（界面、结算）直接读作者对象。

| 表 | 大白话 |
|---|---|
| files | 官方原始文件的镜像。断网时作者加载器从这里拿文件；它就是"镜像数据"本身 |
| kv | 作者程序自己要存的东西：自制包的整份 JSON 和管理记录、屏蔽表。作者网站原本存在它自己的浏览器存储里，我们把存储口子接到这张表。内容格式完全是作者的，不读不改 |
| sets | 官方数据集的安装记录：哪种语言、哪个版本、下载到哪了、占多少空间。插件唯一自己定义的表，只记管理信息 |
| derived | 全量解析结果（作者对象，整个原样）和审计报告。删了能用作者程序重算 |

**kv 里有用户数据**：本地自制、"我的库"是用户自己的内容。旧蓝图规定"完整备份总是包含我的库"，所以导出完整备份时，要把 kv 里的本地自制一起带上。

## 11. 无损的证明：五层审计（全自动，不逐条看书）

数据本身对不对，归作者自己的数据测试管（S1 已在 2.40.0 上全部跑过）。审计只证明一件事：**我们搬运和解析的过程没丢、没改。**

```
 第 1 层  文件镜像：本地 = 云端？
   GitHub 目录树（锁定版本：每个文件的路径、指纹、大小）  vs  files 表
   → 应下载的文件一个不少；每个文件的指纹逐个相同（指纹按 Git 的算法在本地重算）
          │
          ▼
 第 2 层  解析成功：作者加载器每一类、每一本都跑通？
   全量解析两个循环（第 8.2.1 节）→ 每一类、每一本都 0 报错；有报错就原样列出
          │
          ▼
 第 3 层  不漏解析：原始文件里的每一条，解析后都还在？
   直接读原始文件里的每一条记录（不经加载器），用作者编号规则算编号，去解析结果里找：
     A 原始有、解析后也有    → 正常
     B 原始有、解析后没有    ┐ 必须能用原始记录上的"解析标记"解释
     C 原始没有、解析后多出  ┘ （例：物品变体由模板生成、亚种并入种族、_copy、_versions、raw_ 草稿层）
     D 解释不了的            → 可疑清单
          │
          ▼
 第 4 层  只有解析处不同：A 桶的每一对，原始 vs 解析后逐字段比
   允许不同的只有两种：
     ① 加载器加的运行时字段：作者原始数据结构定义里不允许出现的字段（例 __prop）
     ② 原始记录本身带解析标记（_copy、_mod、_versions 等）
   其余任何不同 → 可疑清单
          │
          ▼
 第 5 层  作者搜索索引对账（辅助参考，不当作"没漏"的证明）
   每类编号集合 vs 作者搜索索引（物品加变体副索引）→ 差异列清单
```

**判定依据全部用作者或云端现成的，不手写清单：**

| 要用的东西 | 来自 |
|---|---|
| 云端文件清单与指纹 | GitHub 目录树（锁定版本） |
| 原始文件里哪些顶层键是"一组条目" | 作者结构定义（`5etools-utils` 的 schema）的顶层键 |
| 条目编号 | 作者编号规则 `URL_TO_HASH_BUILDER`，直接用在原始记录上 |
| 哪些是"解析标记" | 作者结构定义里的复制/修改、版本定义（`util-copy.json`、`util-edition.json` 等） |
| 哪些字段是"运行时加的" | 作者原始数据结构定义里不允许出现的字段 |

**可疑清单怎么处理：** 按类别查根因，不按条目修。
- 是加载器有现成入口没用上？用上，然后重跑。
- 是作者自己的规则（例如有意不显示）？注明出处，归入 B/C 桶。
- 都不是？报告驾驶员，停下等定。
- 不手写补数据，不逐条对照原书。

**在哪里跑：**

| 层 | 插件里（每次安装后自动，结果进体检） | 验证程序里（Chrome + WebKit，可随时重跑） |
|---|---|---|
| 第 1 层 镜像 | ✔ | ✔ |
| 第 2 层 解析成功 | ✔ | ✔ |
| 第 3 层 不漏 | — | ✔ |
| 第 4 层 只有解析处不同 | — | ✔ |
| 第 5 层 索引对账 | ✔ | ✔ |

第 3、4 层要用作者的结构定义（`5etools-utils`），这套工具不随插件发布，所以放在验证程序里跑。

审计程序是**检验工具，不处理数据**。它只读四样东西：作者结构定义、作者编号规则、GitHub 清单、解析结果，不含我们自己写的字段名单。

另外两项检验：
- 自制：作者诊断 0 条，或原样列出。
- 断网重启后，第 1、2 层结果不变。

**B3 验证清单（停点 D）**：
- 在 Chrome、WebKit 各跑一遍：五层审计、自制诊断、断网重启、中文官方下载、按书开关、中英自制各装一个、导入一个本地文件。
- 查询、详情、英文原文、搜索、筛选只测数据接口（自动测试，不做界面）。
- 真实 SillyTavern、TauriTavern、iPhone 上需要驾驶员点，步骤由我提供。

## 14. 风险与处理

| 风险 | 处理 |
|---|---|
| 作者筛选、包管理器的某些函数离不开它的网页（例如弹出提示框） | 停下来报告，不手写代替 |

| 某个下载地址失效 | 按源登记表换下一个地址 |
| 英文自制太新，v2.39.0 程序读不了 | 作者流程报错 → 原样显示，进体检，不改数据 |
