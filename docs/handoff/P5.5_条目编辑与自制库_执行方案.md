## 2. 依据与实测过的前提

### 2.1 我的库按体系分、按版本打标签（成熟做法）

- **Foundry**：Actor、Item、Adventure 三类资料包必须写 `system` 字段（本机 `foundryvtt-master/articles/module-development.html`）；每条数据带 `_stats.systemId / systemVersion / coreVersion`（Foundry API `DocumentStats`）；校验由那个规则系统自己的数据结构负责。
- **5etools**：一个体系、一套结构定义，同时管 2014 和 2024。自制包 `_meta.edition` 必填（`report/作者的schema/brew/homebrew.json` 324–334；`util-edition.json`：只有 `classic` 和 `one`）。背景、种族、基础物品、魔法物品变体、职业可在单条条目上带 `edition`。
- **Roll20**：人物是一张没有结构定义的属性表，什么都收。这是反面例子，所以校验不能「是 JSON 就行」。
- **结论**：我的库按「体系」分开存放、分开校验；体系内用「版本标签」区分（和书架同一套：5e / 5.5e / 未归类）。

### 2.2 房规「只记改动」可以直接用作者的 `_copy` 合并

作者合并代码（`vendor/en/js/utils.js` 6233–6241）的规则：

- `_copy` 条目里写了的字段，用这条的（覆盖原件）；
- 写成 `null` 的字段删掉；
- 没写的字段从原件抄过来（作者 `_MERGE_REQUIRES_PRESERVE` 里登记的字段除外）。

所以房规 = `{ _copy 指向原件, 只放改过的顶层字段 }`，删字段写 `null`，原件以后更新时没改过的字段会跟着变。不需要手写 `_mod` 生成器。

### 2.3 撤销不靠回退库的版本链

- 「准备版本 → 发布」保证写入完整，但旧版本会被回收（P5-3 §2.3 第 6 条），不能拿来翻旧账。
- 撤销做法：每次保存前记下这条改之前的样子（反向数据，同基本蓝图 §6「可撤销项带反向数据」），撤销 = 把旧样子再保存一次，同样走「准备 → 发布」。
- 驾驶员定：每条最近 **20** 步，超出的丢最早的。

### 2.4 表单能用作者结构定义，但不能整个自动生成

- 顶层字段数：法术 49、专长 46、种族 54、背景 39、物品 120（作者 `report/作者的schema/brew`）。字段带类型、可选值，大部分有 `description`。
- 正文 `entries` 层层嵌套，自动表单不好用。所以：简单字段用表单，正文用 JSON 框 + 实时预览（作者渲染器）。
- 结构定义用 2020-12 版标准。`json-schema-library` 的 npm 页写支持 2020-12，**没实测**，放到阶段 C 调研。

### 2.5 版本标签（R78，驾驶员定按默认做法）

- **新建**：按当前战役的规则版本自动标（2014 → 5e，2024 → 5.5e），用户可以改。
- **导入**：用包里自己写的 `_meta.edition`；没写的进「未归类」，不按作者的「没写算旧版」去猜。
- **写到哪**：作者结构定义里有条目级 `edition` 的类别写进条目，其余用现有范围归类（来源级 + 单条例外，P3 §2.1）。哪些类别有 `edition` 从结构定义读，不写死名单。
- **作者编辑文档的限制**：作者的可编辑自制文档新建时只有 `{_meta: {sources: []}}`（`utils-brew-base.js` 419–420），而一个文档只有一个 `_meta.edition`，所以不能靠它区分版本。

## 4. 已定的技术细节

- 存放全部用作者格式：可编辑自制文档、`_copy` 房规。插件只存管理数据。
- 结构校验出错时提示并让用户确认，不强行拦截（P5-0 §13.6.8，与作者一致）。
- 中英对照用作者的 `ENG_name`，只提示对上没有，不自动改另一边（G-3b）。
- 「游玩中改次数、数量」不进库编辑，归 P6 人物（P5-0 §8.5 建议；驾驶员没反对，按此推进）。
- 体系指向加在现有 `RuleDefinition` / `scopes.json` 上，不新建登记表。

## 8. 阶段 C 设计（2026-11-13 驾驶员批准）

### 8.1 调研结论

- **5etools 作者编辑器**（`vendor/en/js/makebrew`）：表单 + 实时预览；正文用文字框，一段一行，用作者的 `UiUtil.getTextAsEntries / getEntriesAsText` 转换；草稿 = `{s: 条目原文, m: {isModified, isPersisted, nameOriginal, styleHint}}`，点保存才写进库。缺点：全英文，字段全部摊开，只有 3 类有构建器。

## 10. 查慢 + 找作者引用入口（2026-11-13，只查没改；实测脚本 `work/tmp/probe-slow.mjs`、`probe-pre.mjs`、`probe-b8.mjs` 没有提交，结果在 `work/e2e-lib/p55-c-probe-*.json`）

### 10.1 存一条为什么会慢

用 Chrome 性能分析器（CDP Profiler）录下保存前后全程，并直接调用后端的换算拆开计时（资料夹的可编辑自制里已有整本中文玩家手册）：

| 环节 | 实测 |
|---|---|
| 存这一下本身（写入 + 刷盘 + 重新解析 + 发布 + 插件记录） | 2.5–3.9 秒（冷启动、后台空闲时 2.5 秒；开小窗 0.3 秒，解析 1.3 秒） |
| 每次改动之后后台自动跑一整次结算内核预计算（`PrecomputeQueue` → `KernelPrecompute.run`） | **46–65 秒** |
| ├ 启动 Foundry 内核并载入全部数据（Plutonium `Bundle.js`：`_isExcluded`、`_pCache_addEntityToCache`、`mutateForFilters`） | 约 10 秒，主线程占满 |
| ├ 逐条检查全库 20618 条「换过没有」（每条：取中英对照 → 算编号 sha256 → 读缓存并 gzip 解压） | 约 36 秒 |
| ├ 真正需要换算的 | 2–3 条（就是刚存的那条） |
| └ 每次都换算失败、每次都重试的 | 732 条 |

- 之前测到的 20–28 秒，是保存正好撞上后台内核启动的那 10 秒（抢主线程）。
- 慢的根源在插件自己的预计算排程，不在作者：
  - 一次小改动就全库重查；
  - 查「换过没有」也要解压缓存；
  - 失败的条目不记住，每次重试；
  - 连着存几条，就连着排几整次。

### 10.2 复制件换来源编号：作者没有入口

- 结构定义里标了「来源」类型的字段（`source`、`classSource` 等）和正文 `{@标签}` 能用作者的东西找全。
- 「名字|来源」写在一个字符串里的引用（职业 / 子职特性、起始装备、附加法术、专长……）没有标类型。作者的 `test-tags.js` 是按类别逐个手写的检查代码，只检查不改写；`5etools-utils` 也没有改来源编号的工具。
- 要换就只能自己列一张「哪些字段是引用」的表，而这正是驾驶员禁止的（会漏，变成第二套结构定义）。**结论：复制件不换来源编号。**

### 10.3 不换编号的做法实测（`probe-b8.mjs`）

- **一个包 = 作者的一个自制包**。复制件保留全部原编号，包头 `_meta.sources` 在原来源之外**多登记一行自己的来源**（如 `PHB_COPY2「玩家手册（副本 2）」`）。作者导入时按「来源编号组合」认包（`utils-brew-base.js` `_getBrewId`），所以每份复制件都是不同的包，可以同时存在多份。
- 改其中一份里的一条：照作者改可编辑包的做法（`utils-brew-impl-brew.js` `pPersistEditableBrewEntity`：复制整包 → 换那一条 → `BrewUtil2.pUpdateBrew`），对任何包都适用。
- 实测：
  - 中文玩家手册复制两份，两份同时存在 ✔；
  - 火球术按「同编号不同包」并排出现两份复制件 ✔；
  - 把副本 2 的火球术改成 9 环，副本 1 和官方都没变 ✔。
- 代价：每份复制件的每一条都和官方同编号，每次改动都要重新算全部「同编号的另一版」。两份整本复制件时，存一条要 **22.5 秒**（其中解析 21.8 秒，要处理 1903 条同编号条目）。要靠「只重新解析改过的那个包」来降。

## 11. 后台补换算提速（2026-11-13 驾驶员批准「后台换算先做」；本地提交 48d7b29、15dd7bb，未推送）

- `KernelPrecompute.run({ mode })`：
  - `full`：装 / 更新资料后跑，行为不变，照旧重试失败的条目、清旧行、写「完整」标记；

- 结算内核用到才开。作者有导入器的类别按内核指纹记下（`kc-importable:规则`），以后不为查这个开内核。
- `KernelCache.state`：只数主键、不解压。换算失败记 `kc-failed:钥匙`（同时占住 `kc:` 行，读出来是 null，照旧现场换算并报原错）；后台补换算跳过它，内核或官方数据换过就是新钥匙、自然重试。`sweep` 和回收空间（`reclaim.ts`）一并清旧失败记录；换算成功后删失败记录。
- `PrecomputeQueue`：停手 `quietMs`（后端 5 秒）后才开始跑，等待中连着改只跑一次；`settled()` 连等待的那段一起等。

| 失败条目 | 每次重试 | 第一次后台补换算试一遍（这个资料夹 656 条，33.6 秒，只一次），之后跳过 |

## 12. B8-0 两个旧问题的根因（2026-11-13，只查没改；实测 `work/tmp/probe-b80.mjs`，结果 `work/e2e-lib/p55-c-probe-b80.json`）

两个问题都出在「存入我的库」复制整本书的代码（`copy-source.ts` `copyRawSource`），不是作者数据本身的问题。

1. **「Unresolved "_copy"」（玩家手册复制一份报 348 条）**：作者规矩（`utils.js` `_pDoMetaMerge`；结构定义 `util-meta.json` `internalCopies`）——条目 `_copy` 同一个文件里的条目，包头要在 `_meta.internalCopies` 里声明哪几类，作者才会在本文件里找原件。复制代码只声明了指向别的来源的 `dependencies`，没声明本书内部的。玩家手册里涉及：`background`、`monsterTemplate`、`subclass`、`subclassFeature`、`backgroundFluff`、`raceFluff`。
2. **作者全文搜索崩溃**（`omnidexer.js` 邪术祈唤读 `featureType`）：复制代码扫 `data/` 下所有文件，按顶层名字认条目。作者给 Foundry 用的补充文件（`data/foundry-*.json`、`data/{spells,bestiary,class}/foundry.json`）顶层也叫 `spell`、`optionalfeature`、`classFeature` 等，内容只有效果和动作、没有正文，被当成条目复制了进去（玩家手册：法术 7、可选特性 23、专长 8、动作 4、种族特性 11、职业 1、子职 3、职业特性 37、子职特性 64）。缺 `featureType` 的可选特性让作者搜索建索引时崩溃；同编号的补充记录也会混进复制件。
   - 作者网站代码不读这些文件；Plutonium 是按文件名逐个写死读的。作者没有能直接拿来用的「补充文件清单」。
3. **验证**：实测脚本里临时按文件名去掉补充文件的记录（只为验证，不进代码）、补上 `internalCopies`，重新导入。结果：「找不到原件」从 348 条变成 0 条，作者搜索正常。

### 修法（待驾驶员批准，放进 B8-3「复制成我的」）

- **internalCopies**：复制时条目 `_copy` 指向本书的，把这一类写进 `_meta.internalCopies`（照作者规矩和结构定义）。
- **只从作者实际读的文件里取**：作者网站的加载器都经 `DataUtil.loadJSON / loadRawJSON` 读文件。在小窗里让作者加载这一类条目（`DataLoader.pCacheAndGetAllSite`），记下它实际读了哪些文件，复制时只从这些文件里挑记录。这个清单来自作者的实际行为，不手写。如果有的类别拦不住，就改为在主窗的文件供应处记录，并回来报告。
- **已经存进去的旧副本**（B8-6 迁移时处理）：补 `internalCopies`（只改包头，安全）；补充文件的记录按「和作者补充文件里的记录完全一样」识别后去掉。
