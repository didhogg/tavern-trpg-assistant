## 0. 目标、红线、驾驶员已定的决定

**目标**：给十本核心书与 SRD 里的**每个条目**加一份英文版，放在条目的 `i18n.en` 里；只做数据，不改界面。

**驾驶员已定（不再讨论）**
1. 英文放在每个条目的 `i18n.en` 里（按规格 §5.8）；阶段 F 实测体积，合计超过 10.5 MB 才改成单独的英文附加包，并先报告驾驶员。
2. 范围包含随机表（R9 的 1,097 张）和书籍章节（R12 的 96 章）。
3. 英文**正文一律整段存**（`TextBlock[]` 作为一个字段），不依赖中文块的编号；R14 做完后必须重跑对齐校验。

**红线**
- 已有条目的**中文部分一个字节都不变**：`id、type、name、nameEn、keywords、summary、data` 的哈希与阶段 0 的快照相同；条目只允许多出 `i18n`。
- SRD 包与十个书包里的 `manifest`（含 `dataVersion`）不变。`dataVersion` 升级留给 R15。
- 不联网；英文只来自仓库里的 `reference/5etools-cn-main（数据库）/data-bak/`。
- 不改界面（`src/ui`）；只允许 `src/schemas/pack.ts` 加一个可选字段（第 5 节）。
- 被审计引用的 11 个 `tools/data/convert/` 文件（blocks、common、featRule、foundry、item、items、monster、plan、spell、variants、versions）只允许**末尾追加或单行原地修改**；新逻辑写新文件。
- 官方书籍（`reference/龙与地下城官方资料`）不进数据。
- 不推送、不发布、不安装；推送要驾驶员再次说「可以推送」。
- 不空 catch；单文件 ≤400 行；文档只写现状。

## 2. 总体方案：把整条流水线对着英文数据再跑一遍

不去逐字段手工翻译对应关系，而是**对着 `data-bak` 再跑一遍同一条流水线**（规划 → R11 → R9 → R12 → 转换），得到「英文条目」；再按 `id` 与中文条目配对，把中文 `data` 里带文字的字段在英文条目里的同路径取值，放进 `i18n.en.fields`。

```
 中文 data/ ──▶ planAll/R11/R9/R12 ──▶ convertAll ──▶ 中文条目（8,853）──────────┐
                                                                                    ├─▶ 按 id 配对
 英文 data-bak/ ─▶ 同一套流水线（lang=en）─▶ 英文条目（id 应与中文相同）─────────────┘      │
                                                                                         ▼
                                                      逐字段对齐 ─▶ 条目.i18n.en = { name, summary?, fields }
                                                                  └▶ 对齐率与未对齐清单 → 报告
```

为什么这样做：英文数据与中文数据结构一致（第 1 节），id 由英文名生成，所以同一套代码能产出同样的 id、同样的块结构，行内标记（`{@spell …}` 等）也走同一套解析；英文里的引用会解析到**同一个条目 id**。

**与 `reference/wiki-dnd-parser-master（中英文对换）` 的关系**：它是把 5etools 中英数据导成 wiki 页面的工具，也是「按键配对中英记录」的思路，但产物是 wiki 的 HTML 与 `{{@tag|…}}`，格式与我们的 `TextBlock`、`{{ref:id|…}}` 不兼容；要运行它还得安装依赖（联网），所以**不直接用它的产物**。我们这条路已经是最省事的「对换」：一个环境变量把数据目录换成英文，现有流水线原样产出英文条目，没有任何手工翻译。借用它的两处：①`config/i18n-key-rules.json` 里的 `forceCommonKeys`（与语言无关的键）与本文第 3 节「跳过的键」对照一次，差异写进报告；②它的 `*namelist.json` 思路（id、英文名、中文名成对）不需要，我们的条目已有 `nameEn`。

**英文那一遍的实现**
- 数据目录：`tools/data/extract/load.ts` 的 `DATA_5ETOOLS` 单行改成读环境变量 `TRPG_DATA_DIR`（默认 `data`，英文为 `data-bak`）。`books.ts`、`r11.ts`、`fluff.ts`、`r9Candidates.ts`、`r9Golden.ts` 都经由这个常量取数据，不需另改。
- 隔离：英文那一遍作为**子进程**运行（新入口 `tools/data/english.ts`，环境变量 `TRPG_DATA_DIR=data-bak`、`TRPG_DATA_LANG=en`），只做「规划 + 转换」，把全部条目写成一个临时 JSON（`os.tmpdir()` 下，路径由主进程传入），主进程读回。**不**做输入快照检查、不做 `assertFieldCoverage`、不写包、不写报告。
- 语言开关：`InlineContext` 加可选 `lang?: 'en'`（`tools/data/markup/inline.ts`，不在冻结范围）；`convertAll` 里构造 `inline` 时从 `TRPG_DATA_LANG` 取。`lang === 'en'` 时：`ATK_NAMES` 换成 Melee Weapon Attack 等、`命中：`→`Hit:`、`未命中：`→`Miss:`、`（充能N–6）`→`(Recharge N–6)`。`blocks.ts` 里的全角冒号 `：` 在英文下改成 `: `（单行原地修改，用 `ctx.lang`）。其余中文字面量按第 8 节阶段 A 的扫描逐个处理。
- 英文那一遍没有「驾驶员约定的中文覆盖」（`nameOverrides`、`BASELINE_ALIASES`、`idRedirects` 的中文名条目等）：它们只影响少数 id，对不上的进未对齐清单，**不为此在英文那一遍补中文逻辑**。

## 3. 对齐算法（`tools/data/i18n/align.ts`，新目录新文件）

输入：中文条目 `c`、英文条目 `e`（同 `id`）。输出：`i18n.en` 与统计。

```
alignEntry(c, e):
  name    = e.name        （必须无中文；与 c.nameEn 不同时记 nameMismatch，仍用 e.name）
  summary = e.summary     （只有无中文时才写；写不了的计数，不算未对齐）
  fields  = {}
  walk(c.data, e.data, path = '')
```

`walk(cn, en, path)` 规则：
1. **文字叶子**：`cn` 是字符串且含汉字（`\p{Script=Han}`）：
   - `en` 是字符串、无汉字、无 `{@`、非空 → `fields[path] = en`；
   - 否则记未对齐（原因 `noEnglish` / `enHasCjk` / `enHasTag` / `typeDiffers`）。
2. **块数组叶子**：`cn` 是 `TextBlock[]`（每个元素是含 `p`/`h`/`list`/`quote`/`table`/`tableRef`/`read` 之一的对象）且序列化后含汉字：
   - `en` 也是 `TextBlock[]`、序列化后无汉字、无 `{@` → **整段**存到 `fields[path]`；块数不同也存，但计入 `blockCountDiffers`（报告里单列，不算未对齐）；
   - 否则记未对齐。
3. **普通数组**：`en` 是数组且**长度相同** → 逐下标递归（路径 `traits.0.name`）；长度不同 → 这个数组整体记 `lengthDiffers`，不输出。
4. **对象**：逐键递归；`en` 缺这个键 → 记 `noEnglish`。**跳过**的键（任何层级）：`credit`、`src`、`anchor`、`order`、`ordinal`、`book`、`level`、`kind`、`page`、`titleEn`、`nameEn`。
5. 数字、布尔、不含汉字的字符串：**不输出**（与语言无关）。
6. 中文里含汉字但英文里同位置不是同类型 → `typeDiffers`。
7. 路径格式：对象键用 `.`、数组下标用数字，如 `text`、`lore`、`traits.0.name`、`traits.0.text`、`rows.3.cells.1`、`cols.2`（与规格 §5.8 一致）。

**条目级**：中文有、英文流水线里没有这个 `id` → 记 `noEnglishEntry`，不加 `i18n`；英文有、中文没有 → 忽略（计数写进报告）。

**不能做的事**：不把英文写进中文字段；不改中文条目的任何字段；英文 `fields` 里的值**不再**经过任何中文处理。

## 4. 条目格式

```
entry.i18n = { en: { name: string, summary?: string, fields: Record<string, string | TextBlock[]> } }
```

- `fields` 可以是空对象（只有名字对得上时），`name` 必有。
- 英文正文里的引用是 `{{ref:<同一个 id>|English display}}`。

## 5. 模式与校验器

**`src/schemas/pack.ts`**：`entrySchema` 加 `i18n: z.object({ en: z.object({ name: z.string().min(1).max(240), summary: z.string().optional(), fields: z.record(z.string(), z.union([z.string(), textBlocksSchema])).default({}) }) }).optional()`（`textBlocksSchema` 用 `src/schemas/text.ts` 现有的）。`StoredEntry` 与入库映射**不改**（R15）。

**构建校验（`tools/data/i18n/validate.ts`，对最终条目全量检查，失败即构建失败）**：
1. 每个 `fields` 的 path 在中文 `data` 里存在，且类型一致（字符串对字符串、块数组对块数组）。
2. 英文值里没有汉字、没有 `{@`、没有 `{{ref:` 指向不存在的 id（接入现有 `checkReferences`，扫描 `i18n.en.fields`）。
3. `i18n.en.name` 无汉字。
4. 带 `i18n` 的条目，其中文部分哈希与快照一致（测试里做，见第 12 节）。

**覆盖矩阵与兑现检查**
- `DELIVERED_WP` 加 `'R13'`。
- `validate/delivered.ts` 的 `targetValues` 增加一条：`to` 以 `i18n.en.fields.` 开头时，在条目的 `i18n.en.fields` 平铺键里取值——键里的数字下标换成 `[]` 后与 `to` 剩余部分相等即算命中。
- 206 条 `wp: R13` 的登记要逐条核对并改写（阶段 F）：
  - `…ENG_name → i18n.en.name`（67）：保留；
  - `…entries[].ENG_name → i18n.en.fields.text`（96）：保留（英文标题在 `text` 块里）；
  - 其余 43 条（结构化字段的 `ENG_name`，如 `activities`、`additionalSpells`、`_versions`）：看输出里是否真有对应的 `fields` 键；有 → 把 `to` 改成真实模式（如 `i18n.en.fields.activities[].name`）；没有 → 改成 `dropped`，`kind` 用现有允许值中最贴切的，`why` 写具体理由并带上路径本身（同一句理由不得用于不同字段）；
  - `book.data[].ENG_name`：`to` 改成 `i18n.en.name`。
- 改写后 `npm run check` 里的矩阵测试、`validate.ts` 的规则（`wp`、`to`、`dropped` 理由唯一）全部通过。

## 6. 随机表与书章节的特别处理

- **随机表**（R9，1,097 张）：英文那一遍同样跑 `planR9`。表的 id 来自英文名与页码，可能与中文那遍不完全相同（去重按内容相似度，英文内容不同会影响分组）。阶段 A 的探针要报出表 id 的重合率。**若重合率 < 99%**：停，把重合率与不重合的清单报驾驶员；备选方案是给 R9 候选记录来源指针（文件 + 数组下标），按下标取英文，但这是单独的工作量，不在本文范围。
- **书章节**（R12，96 章）：英文那遍同样跑 `planR12`；章节 id 取自 `contents` 的英文名，锚点由节点 id 生成，**应与中文完全相同**；`h.anchor` 是逐节对齐的依据。英文书里的 `tableRef` 若 id 与中文同位置不同 → 该字段记未对齐，不强行对。

## 10. 停止条件（遇到就停，报驾驶员，不自行变通）

1. 任一类型的 id 重合率 < 99%（表、书除外的类型）。
2. 表或书的重合率 < 99%（备选方案需要驾驶员批准）。
3. 合计体积 > 10.5 MB 或任一包 > 3 MB。
4. 中文条目哈希出现变化。
5. 英文流水线需要改动被冻结文件的多行逻辑。
6. 矩阵改写时发现登记与输出无法对应，且无法用 `dropped` 的合理理由说明。

其余小问题：保留信息、不丢字段，写进报告。

|---|---|---|
| 英文那一遍 | 对着 `data-bak` 跑同一条流水线得到的条目 | 不是翻译，不写入包 |
| `fields` | 条目里「路径 → 英文文字」的平铺表 | 不是嵌套对象 |
| 整段存 | 一个 `TextBlock[]` 作为 `fields.text` 一个值 | 不是按块编号拆开 |
| 对齐率 | 应对齐的文字字段里已对齐的比例 | 不是条目数比例 |
| 未对齐 | 中文有汉字字段但英文没能写入 | 不是错误；要列清单 |

## 14. 易错点

1. 英文里残留中文字面量（命中、充能、全角冒号、表头「结果」「第N列」）会被校验拒绝；先扫描再逐个处理，别放宽校验。
2. 英文那遍的 id 对不上，不要去改中文 id 或加别名；记清单。
3. 环境变量要在**子进程**里设，别在主进程里改常量。
4. `fields` 的值是英文整段文字，不要用中文模板拼。
5. 数组长度不同别硬对。
6. 构建要两次哈希相同：子进程输出与顺序必须确定（按 id 排序后再对齐）。
7. 快照先做，再动代码。
8. 条目 `summary`：英文摘要里含汉字就不写，不算错误。
