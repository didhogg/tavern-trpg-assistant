### S1 缓存（为什么看资料 / 搜索能只读库）

- 键：`pre:<源>:fluff:<类别>`、`pre:<源>:excluded:<类别>`、`pre:<源>:search`。资料基线 = 官方 commit + 已装自制包校验值和；管理摘要 = 范围 / 房规 / 选择等 `manage` 记录。
- 作者搜索器接好的验证：先用作者自己的 `_pDoSearchLoad` 建索引，`toJSON` 存库；新作者小窗只设置作者自己的 `_searchIndex`、`_maxId`、`_CATEGORY_COUNTS`、`_adventureBookLookup`、`_pLoadSearch`，再 `_initReInCategory`；不改作者文件。探路与新测试都逐项对过，结果 0 差别。
- 装中文一次预计算：29,874 条配图描述、65 类屏蔽、搜索索引 12.07 MB，约 3.6 秒（Chrome）/ 3.9 秒（WebKit）；英文约 29,878 条、9.10 MB，约 2.1 / 2.2 秒。
- 缓存结果与现场逐项比：8 类（race / background / class / spell / item / monster / feat / subclass）0 差别；搜索索引载入后与作者现场建索引得分 / 编号 / 分类 / 来源逐项相同。

### S2 编号按人物独立

- 证明脚本 `tests/e2e/library/seed-order.mjs`：同一小窗“先甲后乙”和另一个小窗“先乙后甲”，两个人物的编号 / 进阶选择逐项相同（只把测试服务器顺序分配的 `kernel...` 编号归一化，不归一化作者进阶编号）；先做别的导入再按存档重建，与存档基准 0 差别。
- 根因记录：Plutonium 导入器第一次使用时会初始化并消耗随机数；只在建卡 / 重建前设一次种子不够。现在先 `pGetImporter` 初始化，再按人物种子导入；导入条目和建卡各用同一人物种子。

### S3 换算缓存

- 钥匙：实际喂给 Plutonium 的条目内容摘要 + 数据版本记号 + 插件版本 + 内核输入摘要（manifest / 设置 / 规则）。实测数据版本改掉、条目内容改掉，钥匙都变，不会误命中（`cache-import.mjs`）。
- 命中：同小窗第二次武器 1 ms、法术 1 ms、怪物 18–20 ms；新开小窗武器 6–91 ms、怪物 38–54 ms；结果与第一次现场换算逐项相同。
- 只实测、不实现：装书时预换算核心书（PHB / DMG / MM）。采样 41 条（每类每书取代表），首次导入共 3.33 秒，平均 81 ms/条；按 2014 核心书 2,799 条外推约 **3.8 分钟**、缓存约 **33 MB**（采样数据总量 510,649 B，平均 12,455 B/条）。是否做由驾驶员定。

### S4 人物基准 + 批量建

- 存档 compact 时把每个 `base`（未叠状态的完整人物）存入缓存；读档每个命中就收集起来，全部命中一次 `createDocuments`（`keepId` 保留人物 / 物品编号）再逐个 `applyStateToActor`。
- 5 人：全部命中 Chrome 736 ms / WebKit 799 ms；一人缺失 Chrome 1112 / WebKit 1036 ms；缓存全清 Chrome 3742 / WebKit 4347 ms（仍能读档，结果与存档前一致）。
- 50 人：Chrome 1811 ms / WebKit 1649 ms（同一基准复制 50 份做规模计时，照实报）。
- 5 人第一人扣 3 点血：状态差别叠回后与存档前当前值一致。

### S5 进战役时开机

- `KernelRuntime.enter`：有绑定才开机，先关其他战役小窗；`closeAllExcept` 负责切换。
- `boot.ts` 监听当前归属、内核绑定、只读：有绑定自动 `enter`（不 await、不挡界面）；切换/读档关旧开新；未绑定/无战役/只读/只看资料搜索不开；失败 `console.error` + toast。
- 实测（WebKit）：`enter` 848 ms；切换后只有 1 个小窗；未绑定 0；看资料 / 搜索后 0；开机后第一次攻击 23 ms。
- 离线修复：`KERNEL_MODE_SETTINGS` 的 `import.isNoPrereleaseBrewIndexes=true` 经作者自己的配置迁移搬到 `dataSources`；断网不再请求 raw.githack 的 unearthed-arcana / homebrew 索引。
