总览见 `docs/handoff/D1.2_后续流程大纲.md`。顺序：G1 → **G2 数据可用性体检（只查不修）→ G2.5 数据修正** → G3 显示整理 → D1.2b 导入。

**状态**：框架与已知修法已写好；「待修清单」（第 2 节）要等 G2 四段全部做完、驾驶员看过报告后，由发现登记表（`docs/probes/D1.2-G2_发现登记/`）生成，再交驾驶员审阅批准，才开工。**本文件现在不能据以开工。**

## 0. 目标、红线

**目标**：把 G2 登记的全部 `data-defect` 修掉（`source-defect` 与 `decision` 按驾驶员的决定处理），使发现登记表里的 `data-defect` 清零，后续模块读到的数据都能直接用。较多时分批，每批独立验证、独立提交。

**红线**

- **修在转换代码里，由构建产出**，不手改包。`tools/data/convert/` 下 11 个冻结文件（blocks、common、featRule、foundry、item、items、monster、plan、spell、variants、versions）只允许末尾追加或单行原地修改；新逻辑写新文件。单文件 ≤400 行，不写空 catch。
- **只增不改优先**：能「在旁边加一个解析好的字段」解决的，不改已有字段；必须改已有字段的（主要是 `uses` 误判、怪物断引用），逐条进 `g2-additive` 放行清单并写理由，基线是 G2 开工快照（11 个包的哈希）。
- **新字段一律可选**，`dataVersion` 保持 3；已发布的扩展 0.2.0（提交 `f4eddfe`）必须仍能安装 G2.5 之后的新包——有专门的测试，把 0.2.0 的安装校验代码固定下来对新包跑一遍。
- 数据格式的改动同步 `src/rules/dnd5e2014/data/` 的 zod 模式、`docs/units/D1_数据管线.md`、`docs/包格式说明.md`（涉及包作者的部分）、字段覆盖矩阵。没登记的字段让构建失败（沿用现有规则）。
- 期望值仍来自独立来源（见 G2 文档第 14 节）；**从 5etools 导入的数据，核对时不能拿 5etools 自己当期望值**，要用原书或 D&D 5e API / Foundry 的 SRD 数据。
- 跨包内容一律「扩展包自己登记」；不改界面（界面归 G3）；不跑整套 e2e；不推送。
- 参考材料（`reference/`）只核对，不进数据；要把其数值写进仓库的测试夹具，先问驾驶员。

## 1. 每批的做法与验证

```
 选一批（同一 fixSource、同一类数据）
   ↓ 改转换代码 / zod 模式 / 包格式
   ↓ 构建（TRPG_DATA_TAG=main npm run build:data），两次哈希相同
   ↓ g2-* 测试按新结果更新登记表（该批的 data-defect 减少）
   ↓ g2-additive 通过（改了已有字段的逐条有理由）
   ↓ 旧扩展 0.2.0 装新包通过
   ↓ npm run check、npm run test:data
   ↓ 快速 e2e 子集（库）+ 升级场景（E2E_SUITE=upgrade）
   ↓ 报告写一节，本地提交
```

- 批次顺序按风险从低到高：**① 导入类（5etools 里已有，只需补转换映射）→ ② 读取器与格式扩展类 → ③ 自己结构化类（要对照原书逐条）→ ④ 需驾驶员决定的**。每批做完停下，驾驶员看报告说「继续」。
- **包版本**：G2.5 全部做完后统一升到 **1.4.0**（新增了字段，按语义化版本升小版本）；若 G2.5 分成多次推送，每次推送各升一个小版本。批次之间不推送；推送、刷新目录缓存仍按当次授权。
- 每批的数据有变化时才跑快速 e2e 与升级场景；整套 e2e 只在 G2.5 全部结束且驾驶员同意时跑。
