## 2. 现在的结构

```
 插件页面
   startAuthorFrame({codeSet:'foundry'})      ← 复用作者小窗的宿主代码（src/library/runtime/host.ts）
        │  call('boot', 世界输入)   ▲ 要文件：packs/<包>.json、data/…（由插件 / 【库】回答）
        ▼                           │
 vendor/foundry/frame.html（结算小窗，隐藏）
   frame-early.js        复用：存储隔离；5etools data/ 读取改向插件要
   官方经典脚本 14 个     jquery、pixi、socket.io…（顺序取自官方页面）
   kernel-frame.js       src/rules/kernel/frame/main.ts
     ① 整页加载完才 import scripts/foundry.mjs（否则它自己连服务器启动）
     ② world.ts 组世界数据（服务器下发的形状）；server.ts 本地回答 Socket.IO 请求
        模板=读小窗目录文件  时间=输入的世界时间  资料包=向插件要  写入=记进变更计划
     ③ 官方 Game.initialize；只省画布、键鼠、手柄、音视频、界面渲染
     ④ random.ts：编号随机源按种子确定（同输入同编号）
   systems/dnd5e/dnd5e.js（原代码打包）+ modules/plutonium、modules/lib-wrapper（原包）
```

`vendor/foundry/` 由 `tools/vendor-foundry-kernel.mjs` 生成：跑一次演示站官方完整启动，录下实际取过的文件原样保存（107 个 + 模板 60 个 + dnd5e/模块清单与语言，共 22MB）。清单在 `vendor/foundry/manifest.json`，不要手改。

**标准答案环境已知异常（驾驶员 2026-11-07 定单列）**：怪物动作 Entrap（AATM），演示站原件在 WebKit 上、同一批排在前两条之后转换时报错（只有位置、无说明）；单独转不报错；插件小窗按同样顺序正常转出。两种方法（整批、单条）未查明原因，属原件环境与顺序有关的问题，不计为底座差异。



1. **标准答案此前缺 dnd5e 翻译**：直接把 `system.json` 原文交给官方客户端，语言文件路径 `lang/en.json` 会取到核心语言文件。服务器下发时路径带 `systems/dnd5e/` 前缀；现由 `src/rules/kernel/packages.ts` 统一补前缀（标准答案和小窗共用）。修正前的标准答案里 dnd5e 文字都是键名，已重跑。
2. 官方 v14 迁移旧格式效果时给 `system.changes` 生成随机 `_id`，两次运行不同。小窗和标准答案都装同一个确定随机源（`random.ts`，种子默认 `kernel`）后才可逐项比较；这也让存档里的变更计划编号稳定。掷骰不走这个随机源。

4. Plutonium 的 `module.api` 在 ready 之后异步赋值；`boot` 等它就绪才返回。
5. 小窗 0×0 时官方会报“窗口尺寸不足”，只影响界面；对答案程序把它和 Plutonium 可缺后端的 404 单列，其余报错一律算失败。
