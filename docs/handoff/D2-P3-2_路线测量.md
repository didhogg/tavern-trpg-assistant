## 1. 为什么测

旧蓝图把 dnd5e、midi-qol、Times Up 的计算逐个函数手抄改写，约 60 项。驾驶员指出这是打地鼠式手工活，要求先做一次测量代替逐个评估：
- 路线 A：手工改写 dnd5e 的计算代码。
- 路线 B：写一个 Foundry 底座替身，让 dnd5e 原代码原样跑。

两条路线用同一把尺子量：**真实工作量下实际执行到的源码行数**。

## 4. 结论与限制

**选路线 B**：
- 量约为 A 的 3.4 分之一。
- 写的是通用底座，dnd5e 升级只需重新打包。
- 有官方原件可以一键对答案。

**但 B 本身仍是约 6 千行的手写**：
- 必须按 Foundry 公开文档的行为来写，不能抄 Foundry 源码（商业许可）。
- 用演示站官方原件录制回放，0 差异才算过。

这次**没有量到**的部分，路线 B 还要补测：
1. 写回数据的路径。真正扣血、改状态要走文档更新和数据库后端（`CONFIG.DatabaseBackend`）。插件里要改成“变更计划”。本次只量了计算。
2. midi-qol、Times Up 原样运行要用到的底座（钩子、战斗回合、文档更新等）。
3. 成长记录的“应用”流程（升级时的 AdvancementManager）。本次只读了成长数据。
4. Plutonium 已经在探路运行壳里跑通，它要用的底座和本次清单的重合度还没算。

“行数”是执行到的源码行，不等于要写的行数：路线 A 里也包含数据定义行，路线 B 的清单里还有少量其实用不上的条目。两边口径一致，可以拿来比较。

## 5. 本轮自检（做错的地方）

1. 第一版记录器是我自己写的，靠包住函数来计数。它漏掉了 Foundry 的冻结命名空间（数据模型、字段全没记到），还弄坏了取值器。应该先用浏览器自带的官方覆盖率工具；已改用，并删掉自写记录器。
2. 一开始直接用演示站登录页，那里已经自动启动过，环境不干净，试了几轮才改为同域空白页。
3. 对已经建好的文档又手动调了一次 `prepareData()`，导致重复定义报错。官方在构造时已经自动准备好了。
4. 路径里有空格，文件标记的匹配规则没考虑到，第一次没能拆回源文件。

## 6. 补测（2026-11-07 第二轮）

**midi-qol 一套是否必需（用数据核实）**：不必需。
- 2014 条目转换结果共 35,067 行，用到 midi 专用写法的只有 17 条，用到“按动作到期”的只有 8 条，都来自 PAA 补丁库。
- 主体来源 Plutonium、dnd5e SRD 用到 midi 写法 0 种、特殊持续时间 0 处。
- Foundry 14 本体自带回合/轮次/战斗的到期时机。dnd5e 6.1 自带短休、长休，以及“来源/目标回合开始/结束”到期（`config.mjs:4862–4880`）、受伤自动专注检定（`attributes.mjs:705`）、抗性扣血。Times Up 的功能已被覆盖。
- midi 独有的只剩两样：自动走完攻击→伤害→豁免流程；状态带来的攻击优劣势（midi `conditionRules.ts`，130 行纯数据，MIT）。

**midi-qol 在本环境能否运行（实测，作者正式包）**：不能。

| 正式包 | 版本 | 要求 |
| --- | --- | --- |
| midi-qol | 14.6.8 | Foundry ≥14.369；dnd5e ≤6.0.999 |
| DAE | 14.6.6 | Foundry ≥14.369 |
| libWrapper | 1.13.5.1 | LGPL-3 |
| socketlib | 1.1.4 | MIT |

- 演示站是 14.365，Foundry 判定 DAE、midi“需要更新的 Foundry”（可用代码 10），不予启用。启用后的攻击调用没有执行，目标生命值不变。
- 这里有两处对不上：Foundry 本体版本（演示站太旧，无法通过拉取仓库解决），以及 dnd5e 版本（midi 只认 6.0.x）。
