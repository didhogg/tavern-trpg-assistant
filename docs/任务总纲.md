# 任务总纲

## 1. 产品目标

开发 SillyTavern / TauriTavern 前端扩展「TRPG 跑团助手」：玩家在酒馆中手动管理一场 TRPG 战役，快速掷骰与结算，把已确认的战役事实以省 token 的格式交给 AI，让酒馆 AI 按结果写出剧情。

- 首个规则：D&D 5e（2014）及其官方扩展包。
- 架构对规则通用：规则作为可切换的规则包接入。
- 角色分工：玩家是最终裁决者；规则引擎负责数字（掷骰、加值、HP、资源）；酒馆 AI 负责叙事；DM/KP 助手（进阶版）按规则给出裁决建议，玩家确认后生效。

## 2. 版本与里程碑

## 3. 执行协议

1. 开工：读 `AGENTS.md` → `NEXT.md` → `docs/开发规范.md` §0 → 本文件当前阶段 → 当前 Unit 的单元蓝图。
2. 草案：先在 chat 给驾驶员 ASCII＋大白话草案（目标、红线、验收、四段做法），驾驶员同意后才写文件。
3. 实施：只改当前里程碑范围内的文件；范围外发现写入 `NEXT.md` 的“等驾驶员定”。
4. 验证：按 `docs/开发规范.md` §8 取证；未取得的证据如实标为未验证。报告里的测试结果必须来自**干净工作区**（先提交，再在 `git status` 无未提交改动时跑；不再另开 `git worktree` 副本，见 `docs/开发规范.md` §9）；工作区不干净时先说明，不能把结果当作已提交版本的结果。
5. 收尾：按 `docs/开发规范.md` §0 第 2 条在 chat 汇报（ASCII＋大白话，有界面附截图路径）；更新 `NEXT.md`（≤40 行）；本地 Git 提交。
6. 需要驾驶员决定的事项（规则裁定、范围变化、单元蓝图定稿、真机验收）停下询问，不自行决定。

## 5. 跨里程碑登记（防止遗忘）

- **`supersededBy` 等跨书重印关系**：D2 之后导入非核心书时由管线按写法自动生成，不逐条补。
- **`playable` 的含义**：只作为「玩家严格建卡模式」的参考；解除严格模式后，建人物的种族选择器不受它限制，只是 NPC 种族缺少可玩种族才有的建人物复杂流程数据。
- **被取代的旧版默认隐藏、同名版本切换**：界面等「统一数据库优化」改好后重新构建库页面时做，不在 D1.2a。
- **传奇组 `_versions`**：由 D2 管线按写法处理，不单独开工作包。
- **数据库不写死书目**：书目、依赖、书名都按数据（政策表、包清单）驱动；任何包（官方或自制）走同一套格式与校验；跨包内容一律「扩展包自己登记」，任何包不得在自己的条目里写死别的包的内容（G1）。自制条目编辑器 U11 与全库查询 L1B 是「真正数据库」缺的两块；驾驶员 2026-11-02 定：L1B 排在人物骨架之前；U11 往后放，自己的人物模板先由人物页「存到我的库」（存成怪物条目）解决。
- **统一格式**：D2 P1 定稿的统一格式取代 `docs/模块数据约定.md`，各模块以统一格式为准。
- **只有文字的机制**：照文字显示，不手工结构化（`docs/开发规范.md` §0）。
- **卸载的引用完整性**：目前只提示依赖它的包、不拦截；是否改为拦截或连带卸载，到 L1 第二部分再定。
- **验证节奏**：日常用单元测试、数据测试、快速 e2e 子集与升级场景（新扩展 + 旧书 + 旧目录）；约 35 分钟的整套 e2e 只在阶段收尾且驾驶员同意时跑。
