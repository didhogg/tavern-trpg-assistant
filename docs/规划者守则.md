# 规划者守则（持久记忆）

> 给规划者（云端 Claude）看的。每次开工、每次给驾驶员方案之前先读一遍；再被批评同类问题时，回到这里对照找根因，并把新教训补进来。
> 来源：2026-11-02 驾驶员对人物模块规划的批评（U6 v2.1 → v3.1、L1B、U11、收藏、模板数据结构等反复返工）。

## 一、犯过的错与根因

| # | 错误 | 根因 |
|---|---|---|
| 1 | 先画组件、状态矩阵，再往里塞功能；新建前先弹窗、模板没法先看清再加 | 没从真实用法出发，没先走场景 |
| 2 | 收藏条、撤销令牌、分组折叠、唯一 NPC、命名预览、8 种动效……被骂了才删 | 默认往里加功能，把「四个问题」的过滤推给驾驶员 |
| 3 | 提议「通用条目编辑器（28 种类型）」「新造『人物』条目类型」「把人物转成怪物」 | 没先查现有数据结构与代码：怪物与具名 NPC 本来共用属性块、【我的】库本来有包与条目管理、转换器把怪物装备拆在三处 |
| 4 | 方案一会儿一个样，漏掉已定的「默认未分组」等 | 驾驶员说一句改一处，不回到整体重想，不对照已定决定 |
| 5 | 拆成 U6、外壳、L1B、U11、R1.1……互相依赖；给过一段依赖未完成工作的交接 | 为自己好写而拆，不按「做完能用、批准就能交」来排；提前做「以后可能复用」的通用件 |
| 6 | ASCII 对齐用脚本校验，流程能不能走通却没认真查 | 检查的力气用错地方 |
| 7 | 旧项目的模板入口、回收站批量、标签管理被丢掉 | 没逐条对照驾驶员给的旧规格（它是需求） |
| 8 | 让用户改名 / 删除 / 自建「队伍、NPC、敌人」分类；UNIT1 漏了队伍管理（旧规格 §1.2） | 没想其他系统（队伍状态、给 AI、战斗、地图）要靠这三个固定分类找人；把系统锚点当成普通可编辑数据；又没逐条对照旧规格 |

## 二、以后必须这样做

1. **先查现有的**：动一块之前，读这块现有的数据结构、代码、旧项目规格，写出「已经有什么 / 这次只补什么」。
2. **先走场景**：每个页面先写 3–5 个真实使用场景和点击数；界面上每个东西对应一个场景，对应不上的不放。
3. **先删再给**：每个功能给驾驶员之前先过四个问题（会不会主动用？撤销能不能代替？要不要多记数据？会不会背着改别的数？），过不了的不出现；主动列出删了什么。
4. **不做通用件**：至少有两个现成的使用方，才抽成通用的；各处的搜索、选择按品类各自设计。
5. **数据先同构**：新东西先问「能不能装进现有结构」（例：人物 = 怪物属性块 + 可选字段；怪物装备 = 人物背包），不新造结构。
6. **按「做完能用」分任务**：大任务一次做完；只交批准后马上能执行、不依赖未完成工作的任务；中途发现的问题在任务内修完，不另开小任务。
7. **改一个决定，同一轮对一遍全部相关文档**（`grep` 全文），不留矛盾；改前先读 `docs/decisions.md` 最近几行。
8. **系统锚点不给用户改**：别的系统要靠它找东西的（固定分类、内置包、编号），不开放改名、删除、自建；开放任何「用户可编辑」之前，先列出哪些系统会读它。
9. **交接前逐条对照旧规格的章节目录**，缺一节就说明为什么不做。
10. **流程**：驾驶员没要文档时只给中文 ASCII + 大白话预览；批准后才写文档。面向驾驶员先说结果再说依据，不用自造术语。
